# Security — cross-cutting sweep

**Scope:** synthesizes the dedicated security/deprecation sweep (`_raw/E4-security-deprecation-sweep.md`, verified `V8`) with every security-relevant finding surfaced by territory audits elsewhere in the engagement — diagnostics/provider setup (`A2`, verified `V1`), the runtime-adapter/vendored-kernel boundary and observability (`C2`/`C3`, verified `V4`), messaging and ingress adapters (`C5`/`C6`, verified `V5`), and the bundled composer skill (`G1`, verified `V10`). Every item below has already passed one adversarial verification pass; severities shown are the **verifier-adjusted** ones, not the original auditor's.

## Verdict & posture summary

**Overall posture: B (verifier-adjusted).** The load-bearing security primitives are genuinely good and consistently applied: one shared `assertSafeBind`/`isLoopbackHost` module (`packages/agent-contracts/src/host-safety.ts`) is reused by every HTTP-serving adapter (webhook, openai-api, session-web, tui, live) with `allowNonLoopback` defaulting to `false` everywhere; credential handling in `provider-setup.ts`/`pi-auth-store-inspection.ts` is rigorous TOCTOU-safe engineering (O_NOFOLLOW opens, dev/ino/mtime/ctime snapshot comparisons, exclusive-link atomic promotion); command execution consistently uses `execFile`/`spawn` (argv arrays) rather than shell-string `exec`; and every live instance checked (personal-agent + the a8c fleet; the fleet doc separately counts 9 launchd services) correctly keeps secrets in gitignored `.env` files with `tokenEnv`-style indirection rather than inline in `mono-agent.config.json`.

Against that: **one finding survived adversarial verification as a confirmed v1-freeze blocker** — a license-coherence contradiction (§ below) that makes the "plugin-open" premise legally false as currently shipped. Everything else — a secret-scanning blind spot for the flagship channel's own credential shape, two P1 findings downgraded to non-blocking because they're missing-test gaps rather than shipped defects, a scatter of hand-rolled-N-times security primitives (atomic writes, redaction, lock files), key-based-only redaction that is live today with `includeSensitiveData: true` on the flagship instance, and no automated dependency-vulnerability scanning — is real, worth fixing, and correctly non-blocking under the two-key rule (auditor proposes, verifier confirms; 10 proposed freeze-blockers repo-wide, 2 confirmed, and only this one is security-domain).

## Confirmed findings (verifier-adjusted severities)

### Freeze-blocking

**[P1 — CONFIRMED FREEZE BLOCKER]** — **License coherence for a plugin-open v1.** `packages/agent-runtime/package.json:6` declares `"license": "GPL-3.0-only"` (genuine 674-line GPLv3 `LICENSE` file); `packages/runtime-adapter/package.json` — the *only* package permitted to, and that does, statically import agent-runtime in-process — declares `"license": "UNLICENSED", "private": false, "publishConfig": {"access": "public"}`. 20 of 21 published packages are `UNLICENSED`; there is **no root `LICENSE` file** and no root `package.json` `license` field. `docs/reference/worklab-shared-kernel.md:39` asserts as settled fact that "mono-agent is GPLv3" — a claim the shipped package metadata contradicts.
Verifier (V4) amendment, load-bearing for how this gets fixed: this is **not** a GPL-violation legal catastrophe — Robert owns copyright to every package, so wrapping his own GPL kernel in a differently-licensed facade creates no third-party copyleft violation. The confirmed, decisive problem is narrower but still freeze-blocking: **a publicly-published, "plugin-open" framework whose every non-kernel package grants downstream users zero rights (UNLICENSED), with no root LICENSE, while its own ADR states a different license, cannot make the "plugin-open" premise legally true.** A plugin ecosystem cannot form around UNLICENSED packages. Two-key rule satisfied (auditor C2 proposed, verifier V4 granted the second key on this narrower ground). Fix = maintainer license decision + root LICENSE + consistent per-package `license` fields + ADR reconciliation (§ Actionable steps, SEC-1).

### P1, confirmed as findings but freeze-blocker rejected (two-key rule)

- **Supermemory memory backend gets no liveness check in `doctor`, unlike every other network resource it validates** (`doctor.ts:1375-1426`). Returns `status: "ok"` after a pure config-shape check regardless of the `liveness` flag, while Ollama and Phoenix get real bounded reachability probes. Verifier (V1): real P1 consistency gap, **not blocking** — Supermemory is opt-in/non-default (default = bujo, which *does* get live probes), and the same `ok` output carries an explicit "start the Supermemory instance before sending turns" caveat, so honest ops is not falsified for any default config.
- **`preserveMcpServersUnderOverride`'s security boundary (identity `Set` used to keep `memoryRecall` intact under a tool-policy override) has zero direct test coverage** (`runtime-option-extensions.ts:49-67`); the only test that exercises `composeRuntimeOptionExtensions` never triggers this branch. Verifier (V1): current code is **correct and in production** — a real regression-risk gap, not a shipped defect, so not blocking.
- **Telegram and Slack both run their advanced structural config validation (`readTelegramSendTools`/`readSlackShortcuts`+`readSlackHomeTab`) before the `enabled` early-out**, so a malformed advanced block throws even when the channel is disabled — contradicts each adapter's own documented invariant, and the pattern is doubled across both flagship channels. Verifier (V5): real, doubled bug, **not blocking** — it fails loudly and names the offending field (honest, not silent), the trigger is narrow (malformed structural block *and* disabled), and no v1 DoD clause requires disabled channels to skip structural validation.

### P2, confirmed

- **`createMonoRuntime`'s sandbox injection is silently overridable via an ordinary object-spread key collision** (`runtime-adapter.ts:217`: `{ sandbox: monoSandboxImpl, ...hostOptions }` — a `sandbox` key in `hostOptions` wins because it spreads last). Verifier (V4) downgraded **P1→P2, freeze-blocker rejected**: no in-repo call site passes a `sandbox` key today (only `sandboxPolicy`/`sandboxEngine`); the kernel's `passthroughSandbox` fails **closed**, so an accidental collision breaks availability, not security; and the only actor who can pass options to `createMonoRuntime` is the host author, who already controls the process. Real one-line hardening (SEC-4), not a blocker.
- **Observability redaction is field-key-based only; free-text is never content-scanned, and this is live today.** `redact()` (`packages/observability/src/redaction.ts:40`) only redacts when a JSON key matches `/(token|secret|password|authorization|api[_-]?key|cookie)/iu`; a bare string (user input, compiled system prompt, assistant text, tool-result prose) falls straight to `truncateString` with no secret-*shape* scan. Verified live (read-only, no values printed): `~/personal-agent/mono-agent.config.json` sets `observability.exporters[0].type: "phoenix"` with `includeSensitiveData: true`, meaning full user input/assistant replies/system prompt export to a separate Phoenix service with only key-based redaction as a backstop. Loopback (`127.0.0.1:6006`) bounds network exposure, but content still crosses the process boundary into Phoenix's own storage. Docs (`docs/observability/phoenix-and-backfill.md:35`) calling this "redacted" overstate what a flat string actually gets. Verifier (V4): CONFIRMED, P2, correctly not freeze-blocking (loopback + config-gated + owner's own instance).
- **Two independently-drifted secret-redaction implementations straddle the readiness-probe worker trust boundary** (`readiness-probe.ts:153-197` `safeMessage`/`redactionValues` vs `readiness-probe-worker.ts:135-177` `safeWorkerMessage`). The worker's is strictly stronger (adds a blanket env-value scan and a generic 24+-char token catch-all); the parent's weaker pass runs second, so a gap in the worker's redaction has no independent second line of defense, and a future edit to one won't propagate to the other.
- **Only `openai-api-adapter` re-validates the actual OS-resolved bind address after `listen()`**; `webhook-adapter`, `tui`, and `live` all call `assertSafeBind` pre-listen (correctly) but never re-check `address.address` afterward, so none of the three defends against the OS resolving a configured host string to an unexpected concrete address post-bind. Cheap, cross-cutting asymmetry across four otherwise-consistent siblings.
- **`operator-adapter`'s `live/config.ts` has zero dedicated tests, unlike every sibling config module** — critically, this includes `redactLiveAdapterConfig` (`live/config.ts:72-81`), which exists specifically to keep an `apiKey` secret out of config-view output. The only reference anywhere is a `typeof`-only check (`public-api.test.ts:27-28`); real coverage confirms lines 73-81 (the redaction body) are never executed by any test. `tui`'s identical-shape sibling *is* fully tested, including its own redaction path.
- **No dependency-vulnerability scanning anywhere in CI** — no `pnpm audit`/`npm audit` step, no `.github/dependabot.yml`, no `dependency-review-action`. The only OSS-hygiene gate (`scripts/check-oss-hygiene.mjs`) is a PII/consumer-fixture scanner, not a CVE scanner, despite its name inviting that assumption. For a framework publishing 21+ npm packages, there is no automated signal on a transitive-dependency CVE.
- **`assertSecureRegularFile`'s blanket `stat.nlink !== 1` rejection** (`runtime-adapter/src/sandbox-managed.ts:245`) matches an already-filed, still-open compatibility gap (GitHub issue #191, filed as a #185-security-review follow-up): single-link enforcement is correct for the private managed SRT tree but can wrongly reject a legitimate external Node launcher (NVM/Homebrew/hosted toolcaches) that happens to be hard-linked, since multiple hard links alone don't grant another principal write access. Verifier (V4): code still matches the issue exactly; correctly filed, correctly still open, not a new finding — carried forward, not double-counted.
- **The bundled composer skill's "exhaustive" reference tables omit the web-PWA auth surface.** `feature-coverage.md`'s `mono-agent web` entry lists only `[--host] [--port] [--no-open] [--allow-non-loopback] [--include-memory]`; it omits `--show-auth-url`, `--max-runs`, and the `MONO_AGENT_WEB_AUTH_TOKEN` env var that non-loopback binding requires outside an interactive terminal (all three are real, documented in `feature-registry.md:158`). An operator composing an agent from this skill alone would not learn that binding the PWA non-loopback needs a token. Verifier (V10): confirmed, real completeness gap in a security-adjacent surface; not freeze-blocking (the underlying binding safety code is correct — see Bindings & exposure below — this is a documentation-discoverability gap in one bundled reference, not a broken control).

### P2/P3, confirmed — hand-rolled-primitive duplication (cross-cutting theme, not three separate bugs)

Three independent territory audits (`A1`/CLI, `A2`/diagnostics, `A3`/runtime-host — all verified in `V1`) each flagged the *same* anti-pattern from a different angle: this codebase repeatedly hand-rolls a hardened filesystem/security primitive instead of sharing one implementation.
- **Atomic secure-write implemented twice**: `atomicReplaceFile` (`init.ts:1189`, async-fs) and `atomicWriteManagedExact` (`project-skills.ts:487`, sync-fs) are independent TOCTOU seams for what should be one hardened primitive.
- **Secret redaction implemented twice** across the readiness-worker trust boundary (see above).
- **Owner-private lock file implemented four times**: `acquireBackgroundWorkerLease` (`bg-worker-lease.ts:91`), `acquireFilesystemLifecycleLock` (`background.ts:1369`), `acquireRuntimeLock` (`bg-runtime.ts:1318`), `acquireInstallLock` (`sandbox-manager.ts:1043`, plus a separate `acquireInstallGuard` flock) — real correctness-fix-propagation risk: a hardening fix to one lock implementation has no mechanism to propagate to the other three.

None of these are exploited today (each individual implementation was independently judged sound), but a single shared, tested primitive would remove the drift risk permanently instead of relying on four authors staying in sync by memory.

### P3, confirmed (lower-priority hygiene)

- `pi-oauth-login.ts`'s `auth.json` write (`:75-81`) has no `O_NOFOLLOW`/`lstat` symlink guard, inconsistent with every other touchpoint on the same file in this area; low risk today because production always routes through a private `mkdtemp` staging directory first, but the directly-invokable `pi-oauth-login-main.js <provider>` CLI entry point has no such protection if ever run against an untrusted cwd.
- `redactSlackAdapterConfig` is exported but has zero consumers outside its own test — a redaction helper nobody calls is a drift risk if the config shape it protects ever grows a real secret field.
- Slack has no analog of Telegram's `log-redaction` defense-in-depth layer — no active leak today, but a real parity gap between the two flagship channels.
- `webhook-adapter` is the only HTTP-bearing sibling with no built-in `apiKey`/bearer-auth option (unlike `openai-api-adapter`, `tui`, and `live`, which all support one) — honestly disclosed in its own README/docs ("put it behind a reverse proxy or auth layer you control"), but it is exactly the adapter most likely to need real non-loopback exposure to receive third-party provider callbacks.
- npm publish carries no provenance attestation and authenticates via a classic long-lived token, not OIDC trusted publishing (§ Supply chain — already tracked, not a fresh finding).
- `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` exempts 11 pinned packages from a `minimumReleaseAge` guard that is never actually turned on anywhere — a security control that looks active but gates nothing (§ Supply chain).
- Permissions are split across the 8 live `a8c-agents` instances: 3 of 8 `.env` files (`activity-digest`, `p2-watcher`, `slack-sweep`) are mode `644` (world/group-readable) while the other 5 plus `~/personal-agent` are `600` (§ Live-instance secret hygiene).

## Secret-scanning gap

**gitleaks — the sole automated secret scanner, run identically in CI (`.github/workflows/ci.yml:48`, pinned `ghcr.io/gitleaks/gitleaks:v8.30.1`) and locally (`pnpm run check:secrets` → `scripts/check-secrets.mjs:8`) — has no rule for Telegram Bot API tokens, and its generic catch-all fails on that exact token shape.** `.gitleaks.toml` defines no custom `[[rules]]`, only allowlists.

Reproduced empirically by both the original auditor and the verifier (V8), independently, in isolated scratch repos with the pinned gitleaks binary, never touching the real token:
- A random 40-char secret under a `token =` key **is** caught by the `generic-api-key` rule.
- The bare 35-char tail alone (no leading `digits:`) **is** caught.
- The exact real-world Telegram bot-token shape embedded in JSON — `{"telegram":{"botToken":"<digits>:<35-char-tail>"}}` — is **missed** (`no leaks found`). The embedded colon breaks the `generic-api-key` regex's capture.

Telegram is this framework's flagship channel, so this is a real hole exactly where the threat model needs coverage most. Verifier severity: **P2 (down from the auditor's P1)** — no secret is committed, the primary control (gitignore + `tokenEnv` indirection, followed by every live instance) is sound, and the gap only bites on a *future* mistake (`git add -f`, or a lost `.gitignore` entry).

**NEW-1 (verifier addition, strengthens the finding rather than softens it):** the verifier proved `gitleaks dir` does **not** respect `.gitignore` — a bare secret in a gitignored, untracked file is still flagged. This means the real, untracked root `mono-agent.config.json` (see below) **is** scanned on every CI/local `check:secrets` run and **silently passes** — the "no leaks found" result on the real repo is genuinely the regex gap firing on a live scan, not a skipped file. The gate touches the real token every run and waves it through.

Its only concrete manifestation today: `mono-agent.config.json` at the repo root holds a real 46-character Telegram bot token matching the vulnerable shape. This file is **untracked** (`git ls-files` → empty), **never committed** (`git log --all --oneline` → zero commits), and correctly listed in `.gitignore:17` — confirmed by both auditor and verifier as the maintainer's own gitignored dev config working exactly as designed, not a leak. Its only function in this audit is demonstrating F1's mechanism against a real token (value never printed, never will be). Verifier re-labeled the auditor's "P0-adjacent" framing down to **informational/P3** — it is not a live leak and not a freeze-blocker.

## Bindings & exposure

The **code-level default is safe across every HTTP-serving surface**: webhook, openai-api, tui, live, and session-web all bind `127.0.0.1` by default and all funnel through the same shared `assertSafeBind(host, allowNonLoopback, ...)` (`packages/agent-contracts/src/host-safety.ts`) before `listen()`, refusing any non-loopback host unless `allowNonLoopback: true` is explicit. `openai-api-adapter` additionally requires an `apiKey` for any non-loopback bind. The one `0.0.0.0` reference in the codebase is a documentation example that correctly pairs it with `allowNonLoopback: true` and an explicit caution callout about the required API key — a guarded, deliberate opt-in, not an unsafe default.

Two real, narrow gaps sit on top of that sound foundation:
1. **Only `openai-api-adapter` re-validates the actual OS-resolved bind address after `listen()` resolves** (`server.ts:307-323`); `webhook`, `tui`, and `live` all call `assertSafeBind` pre-listen but never re-check `address.address` afterward, so none of the three catches the OS resolving a configured host string to an unexpected concrete address post-bind. (P2, above.)
2. **The composer skill's reference tables under-document the web-PWA's auth surface** — `--show-auth-url`, `--max-runs`, and `MONO_AGENT_WEB_AUTH_TOKEN` are real and load-bearing for safe non-loopback PWA exposure, but absent from `feature-coverage.md`. An operator composing purely from the bundled skill would not learn a token is required. (P2, above.)

`webhook-adapter` remains the one HTTP sibling with no built-in bearer-auth option, honestly disclosed as a "put it behind your own reverse proxy" design choice — worth closing given it's the adapter most likely to face real external exposure (P3).

## Redaction boundaries

Redaction in this codebase is **key-name-based, not content-based**, everywhere it's implemented, and this pattern is duplicated with independent drift at two separate trust boundaries rather than shared from one utility:

- **Observability** (`packages/observability/src/redaction.ts`): `SENSITIVE_KEY_PATTERN = /(token|secret|password|authorization|api[_-]?key|cookie)/iu` redacts by JSON key only; bare strings (user input, system prompt, assistant text, tool-result prose) only ever get `truncateString`'d — no scan for secret-*shaped* content embedded in free text. This is **live today**: the flagship `~/personal-agent` instance runs its Phoenix exporter with `includeSensitiveData: true` (kind/config confirmed read-only, no values read or printed), meaning full user input/assistant replies/system prompt cross the process boundary into Phoenix's own storage with only this key-based backstop. Loopback binding bounds the network exposure; it does not bound the content exposure once it's in Phoenix's own retention. Docs describing this as "redacted" overstate what a flat string actually receives.
- **Readiness-probe worker boundary** (`readiness-probe.ts` `safeMessage`/`redactionValues` vs `readiness-probe-worker.ts` `safeWorkerMessage`): the worker-side implementation is strictly stronger (blanket env-value scan + generic 24+-char token catch-all) than the parent-side pass that runs after it — two independently-maintained regex sets on either side of one trust boundary, with no shared test proving they stay equivalent.
- **Slack has no analog of Telegram's `log-redaction` layer** — a parity gap between the two flagship channels, not an active leak.
- **`redactSlackAdapterConfig` and `redactLiveAdapterConfig` are the two redaction functions with the weakest safety net**: the former is exported but has zero consumers anywhere (drift risk if the config it protects grows a secret field nobody updates the redactor for); the latter is the *only* sibling redaction function with zero direct test coverage — `live/config.ts` lines 73-81 (the entire redact-the-`apiKey` body) are never executed by any test in the repo, while the structurally-identical `tui/config.ts` redaction path is fully tested.

None of this is a demonstrated leak — every case above is a defense-in-depth/consistency gap on top of a sound primary control (config-gating, loopback binding, or an untested-but-currently-correct implementation) — but a single shared, tested `redactSecrets()` utility used at every boundary (worker, observability, per-adapter config-view) would remove the recurring drift risk instead of relying on N independently-maintained regex sets staying in sync.

## Live-instance secret hygiene (paths + kinds only, values never read or reproduced)

All read-only inspection; no secret value was read, printed, or reproduced anywhere in this audit.

- **Every live instance** (`~/personal-agent` + the `~/a8c-agents/*` fleet) correctly keep provider/channel secrets in gitignored `.env` files, referenced from `mono-agent.config.json` via `tokenEnv`-style name indirection rather than inline values — this is the established good pattern and every instance follows it.
- **File-permission split across the 8 `a8c-agents` instances**: `.env` for `activity-digest`, `p2-watcher`, `slack-sweep` = mode `644` (world/group-readable); the other 5 instances plus `~/personal-agent` = mode `600`. The same split mirrors onto the paired `mono-agent.config.json` files (3× `644` / 5× `600`), though those `644` config files hold no inline secrets, only `tokenEnv` name references — so the immediate blast radius is confined to the `.env` files. Single-user Mac, so real-world exposure is low; still worth normalizing to `600` (SEC cleanup, below).
- **Root `mono-agent.config.json` (repo, not a live instance)**: untracked, never committed, gitignored, holds a real Telegram bot token (46 chars, shape-consistent) as the maintainer's own scratch/dev config. Working as designed, but it is the one place the maintainer's own local practice diverges from the fleet's established `tokenEnv`-indirection pattern — worth a documented convention so future local dev configs don't inline secrets even when gitignored (SEC cleanup, below).
- **Phoenix `includeSensitiveData: true` on `~/personal-agent`** — a config *setting*, not a secret, confirmed read-only from the instance's own `mono-agent.config.json`. Its consequence (full turn content exported to a loopback Phoenix service) is covered under Redaction boundaries above.
- **No other live-instance secret-hygiene issues found** in this sweep beyond the permission split above; shared `~/a8c-agents/.{proactive,control,a2a,brain}.env` files are all `600`.
