# Live instance — `~/personal-agent` (flagship, deep)

**Sources:** `_raw/F1-live-personal-agent.md` (auditor) + `_raw/verified/V9.md` Part A (adversarial verifier, refute-not-ratify stance, read-only re-checks against the live instance). Every grade and finding below is the verifier-adjusted position, not the raw auditor's alone.

## Overview

This is mono-agent's most mature live deployment: a 24-skill, multi-channel (Telegram/WhatsApp/GWS), multi-account personal assistant run from one `mono-agent.config.json`, with `memory.mode: bujo`, native `notify: true` delivery, and `mcpRequestContextServers` all in active daily use. The verifier independently re-opened every cited file/line/byte-count in the raw audit and found the evidence unusually solid — almost every citation reproduced exactly on re-check. Corrections were severity/scope nuances (mostly downward), not fabrications, and **zero freeze-blockers were confirmed** (V9 headline, two-key rule applied). The system's defining trait, confirmed independently: it fails loud and self-heals rather than faking success — every rough edge below produced a log line, not a silent wrong answer.

The raw auditor's top-line grades (**Overall maturity B+, Framework-fit B**) stand unchanged after verification; what moved is confidence and precision at the finding level, plus one cross-instance theme (shared with the `a8c-fleet` audit) that the verifier elevated into an explicit framework-fit observation: **mono-agent ships no honest-ops observability primitives** — no launchd log-rotation/size caps, no crash-loop breaker, no channel-restart-churn signal, no delivery-SLO alerting. Both live instances hit this gap independently; personal-agent took the larger blast radius (1.23GB unrotated log vs. a8c's 27-line logs on a custom host).

## Grades (verifier-adjusted)

### Memory quality — B+
Evidence: `.mono-agent/memory/index.md`, `daily/2026-07-15.md`, `.index/manifest.json` all read in full — same-day capture, zero capture backlog, and a documented 2026-07-14 rebuild (`policyVersion: mono-agent-memory-rebuild-v1`, `parsedSourceItems: 2422`) with its own audit trail (`legacy/` kept deliberately, confirmed load-bearing by V9). Held below A by two verifier-uncontested nits: entity-normalization noise in the `index.md` preview (near-duplicate typed rows for the same real-world referent, actionable item FF-4 below) and two unbounded `memory forget` backup snapshots already at 40MB+ with no pruning policy (V9-confirmed exact size). Neither is a correctness defect — both are preview/hygiene erosion against the "clean memory + a way to preview it" premise clause.

### Skill usage — B+
Evidence: all 24 `skills/*/SKILL.md` directories match `AGENTS.md`'s single-owner registry table 1:1 (raw auditor's coverage note; this specific 1:1 claim was not independently re-run by V9, so it carries auditor-only confidence, not verifier confidence). What V9 did independently confirm: 7 cron jobs and 3 webhook files (2 deliberately `enabled: false` path reservations, confirmed load-bearing), disciplined `overlap: skip` cadence tuning that measurably improved after a 2026-07-10 change, and correct use of `mcpRequestContextServers`. Docked from A because two skill-adjacent surfaces have live, dated gaps: `voice-capture`'s documented MCP fallback is currently broken (F5) and `telegram-notifications`' documented quiet-hours promise doesn't hold on one of two delivery code paths (F4) — both are written-promise-vs-code contract gaps, not usage failures.

### Run success — B
Evidence: V9 independently reproduced the chronic Telegram `getUpdates` churn order-of-magnitude (276 restart cycles in ~6 days of current log ≈ 46/day, consistent with the auditor's ~130/day-over-5-weeks once the larger rotated `.err.log.1` is included) — every cycle self-heals, zero confirmed message loss. The historical cron skip-rate claim (F6) was **downgraded by V9 to PLAUSIBLE/P3**: the *mechanism* (documented `overlap: skip` semantics) is confirmed, but the auditor's specific pre-2026-07-10 tallies were not independently reproduced (the source log is rotated and current logs defeat cheap `grep -c`). Post-cadence-change, the renamed `focus-scan` job is healthy (22 finished/1 skipped). Docked from A by the currently-broken voice-capture MCP fallback (F5, CONFIRMED, 34 fatals in current log vs. 0 in the prior 3 weeks — a real, recent, narrow-surface regression).

### Framework-fit — B
Evidence: raw grade B carried through verification unchanged. The config-first primitives (cron/webhook-as-files, allow-all tools, `memory.mode: bujo`, native `notify`) genuinely deliver the "one operator, one config folder" premise — V9 does not challenge this. What V9 *strengthens* beyond the raw framing: (a) NEW-3 elevates F5's `transcribe-mcp` fatal from "instance config issue" to **plausibly a framework bug** in `mcpRequestContextServers` trust-context propagation for channel-originated turns — worth a framework-repo issue, not just an instance fix; (b) the observability-primitive gap (log rotation, crash-loop breaker, channel-health, delivery-SLO alerting) is now cross-instance-corroborated (both personal-agent and a8c-fleet hit it independently), which is stronger evidence of a real framework gap than a single-instance nit would be.

## Findings (verifier statuses)

**F1 [P1, borderline P2] [verifier: CONFIRMED]** — 1.23GB of launchd stderr accumulated unrotated. `stat` reproduces exactly **1,233,420,489 bytes** for `com.mono-agent.personal-agent-059657c8.err.log.1`; current `err.log` = 656,383B; `out.log`/`out.log.1` = 2.36MB/7.76MB. Plist has no rotation directive; launchd never rotates by default. V9 severity note: unbounded-growth trajectory justifies P1, but zero operational impact to date (disk has room) makes it arguably P2 hygiene. Minor imprecision: the raw finding's "three code-provenance eras" parenthetical actually enumerates two — cosmetic, immaterial. Premise: "honest ops."

**F2 [P1, borderline P2] [verifier: CONFIRMED]** — Admin/watchdog tooling (`bin/mono-agent:7`, `bin/agent-watchdog:25`, `bin/session-web:5`) hardcodes the mutable monorepo checkout's dist, not the pinned `~/.mono-agent/runtimes/agent-app/0.11.2/...` snapshot the live plist actually serves from. Line-exact verified; no live drift today (both 0.11.2). Real latent hazard specific to this machine (framework repo == dev machine): a broken WIP `pnpm build` would decouple the every-15-min watchdog health check from what's actually serving. V9 note: `bin/mono-agent`'s own comment says it deliberately tracks the checkout for Node-ABI parity — intent is partly by-design, so P1 is defensible on this machine's coincidence, P2 in general. Premise: correctness / false-health-signal risk.

**F3 [P2] [verifier: CONFIRMED]** — Chronic `getUpdates` timeout/restart churn is invisible outside raw logs. Current `err.log`: 276 "Telegram channel degraded" events over ~6 days (~46/day); `.err.log.1` carries the historical bulk (auditor's ~4,254 over 3 weeks). Order-of-magnitude "~130/day over 5 weeks" holds. Self-heals every time; `bin/agent-watchdog` checks process-liveness only, no condition on this churn rate. Premise: "honest ops."

**F4 [P2, narrow live exposure] [verifier: CONFIRMED]** — Documented quiet-hours "silent delivery" promise (`skills/telegram-notifications/SKILL.md:22-23`, 23:00–07:00 Europe/Rome) is not implemented on the heartbeat/callback delivery path. `bin/lib/telegram-alert.mjs`'s `sendNativeTelegramCard` (line 127) posts a raw `fetch` and never sets `disable_notification`; zero hits for `disable_notification|quiet|Europe/Rome` in that file. V9 narrowed the live exposure: the heartbeat cron's own schedule (`15,45 7-21 * * *` + `0 22 * * *` = 07:15–22:00) doesn't overlap quiet hours, so the cron path itself is safe today — the real gap is documented callback re-delivery (taps on old cards up to 30 days later) firing an audible push at, e.g., 02:00. Genuine written-promise-vs-code gap in the attention-protection premise clause.

**F5 [P2, framework territory] [verifier: CONFIRMED]** — Voice-capture's documented MCP fallback is currently broken. Current `err.log`: 34× `transcribe-mcp: fatal: missing trusted producing conversation context` + 24× `mcp_init_failed … Connection closed`; the prior 3-week `.err.log.1` has 0 — a recent regression correctly correlated to `mcpRequestContextServers`. Fails loud, does not fake success. **V9 NEW-3**: this is plausibly a **framework** bug in trust-context propagation for channel-originated (Telegram) turns, not merely instance config — worth an explicit framework-repo issue, since any consumer using request-context MCP servers could be affected. Listed by V9 as a "closest-to-blocker" candidate but explicitly NOT a blocker (fails loud, narrow >2-min-voice-note surface, no data corruption).

**F6 [P3, amended from implied P2] [verifier: AMENDED → PLAUSIBLE]** — Historical cron overlap/skip rate was high before the 2026-07-10 cadence change. Mechanism CONFIRMED (documented `overlap: skip` semantics; skip events only surface in raw logs). The auditor's specific historical tallies (e.g. `focus-scan-hourly` 59 finished/18 skipped) were **not independently reproduced** — the source log is rotated and current `out.log` entries are large per-run JSON blobs that defeat cheap `grep -c`. Post-change health (22 finished/1 skipped for the renamed `focus-scan` job) is a retrospective observability note, not a live defect. Downgraded from implied-P2 framing to P3.

**F7 [P3] [verifier: CONFIRMED]** — `openaiApi` (`0.0.0.0:4312`) and Session Web (`0.0.0.0:4599`) are LAN-wide, not tailnet-restricted like the webhook (`100.64.103.59`). Config and `lsof` both verified; both surfaces are bearer-token-authenticated. Minor correction: the raw finding cited the webhook port as `:4313`; the live port is `:4315` — immaterial. A documented, conscious choice (README "Conscious decisions" section), not a silent bug; the asymmetry with the webhook's own stated rationale is worth closing given the unsandboxed, allow-all-tools profile behind it.

**F8 [P3] [verifier: CONFIRMED]** — Retired `heartbeat-prefilter` surface is still partially live. `bin/agent-watchdog:10` live-imports `readHeartbeatState` from `./lib/heartbeat-prefilter.mjs`; `runHeartbeatPrefilter()` deliberately throws; `shouldRunHeartbeat` is used only by the dead binary + tests. **V9 amendment (narrows the cleanup, not the finding):** of the four re-exports the raw audit said "must be kept," only `readHeartbeatState` (the wrapper adding `nativeDeliveries`) is actually consumed — `heartbeat.mjs` imports `readHeartbeatState`/`writeHeartbeatState` directly from `heartbeat-state.mjs`, bypassing this file entirely. So `writeHeartbeatState`/`defaultHeartbeatState`/`HEARTBEAT_MAX_FUTURE_SKEW_MS` re-exports here are themselves unused too — the cleanup is easier than originally stated. Legibility nit: a "retired" module with one live import path.

**Freeze-blocker check:** V9 headline — zero freeze-blockers confirmed across both live-instance audits; every actionable row below is `Freeze-blocking: n`. F5 (transcribe-mcp fatal) is the closest candidate and is explicitly ruled out (fails loud, narrow surface, no data loss/corruption).

## Quarantine

Nothing in this instance's audit was refuted outright. Two claims remain **unproven** (not independently re-verified by V9 this pass — harmless if true, out of scope to chase further before freeze):

- `~/.pi/personal-agent/settings.json`: `defaultModel: "qwen3.6"`, `defaultProvider: "ollama"` — vestigial `pi` CLI init defaults, claimed harmless since actual routing is governed by `mono-agent.config.json`'s `runtime.model`/`fallbackModels`. V9: not independently re-verified this pass.
- `.mono-agent/great-triage-2026-07-11.applied.log` / `.before.tsv` — one-off bulk-cleanup operation logs sitting loose at the `.mono-agent/` root, claimed harmless clutter. V9: not independently re-verified this pass.

One finding is quarantined at partial confidence rather than full confirmation:

- **F6's exact historical cron tallies** (e.g. `focus-scan-hourly` 59 finished/18 skipped) — the *mechanism* (documented `overlap: skip` semantics) is verifier-confirmed, but V9 could not independently reproduce the specific pre-2026-07-10 counts (source log rotated; current logs are large per-run JSON blobs that defeat cheap `grep -c`). Treat the tallies as auditor-reported, not verifier-reproduced; the post-change health improvement (22 finished/1 skipped) is independently plausible given the documented cadence change.
