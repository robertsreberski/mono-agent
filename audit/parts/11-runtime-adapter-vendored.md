# 11 · runtime-adapter & vendored agent-runtime boundary

**Scope:** the `runtime-adapter` facade and its single permitted static dependency, the vendored (worklab-shareable) `agent-runtime` kernel — package boundary, sandbox/SRT injection, exports surface, licensing.
**Maturity grade:** B (verifier-adjusted). The engineering at this boundary is genuinely strong — a compile-time structural contract test keeps the facade's hand types honest against the vendored kernel's generated types, the sandbox/SRT code is unusually careful supply-chain-integrity engineering (hash-pinned managed tree, monotonic policy merge, fail-closed everywhere, 43+ dedicated tests), the one-package-may-depend-on-agent-runtime rule is mechanically enforced by `check:architecture`, and the vendored kernel is fully readable hand-authored source, not an opaque bundle. The verifier confirmed one real freeze-blocker (license coherence for a plugin-open v1) but reframed it away from a GPL-violation scare and downgraded the sandbox-injection footgun from P1/"most security-relevant seam" to P2 latent hardening with no exploitable path. No other findings changed severity; the "76-subpath" recon figure was corrected to 25/22.

## Findings

**F1 — [P1, freeze-blocking] [verifier: CONFIRMED, reasoning amended]** — `packages/agent-runtime/package.json:6` vs `packages/runtime-adapter/package.json`, plus `docs/reference/worklab-shared-kernel.md:39`.
`agent-runtime` declares `"license": "GPL-3.0-only"` (with a genuine 674-line GPLv3 LICENSE file); `runtime-adapter` — the only package permitted to, and that does, statically import it in-process — declares `"license": "UNLICENSED", "private": false, "publishConfig": {"access": "public"}`. 20 of 21 published packages are UNLICENSED; there is no root `LICENSE` file and no root `package.json` license field. The ADR states as settled fact that "mono-agent is GPLv3," which contradicts the shipped metadata.
> `"license": "UNLICENSED", "private": false, "publishConfig": { "access": "public" }`

Verifier amendment: this is **not** a GPL-violation catastrophe — Robert owns copyright to every package, so wrapping his own GPL kernel in a differently-licensed facade creates no third-party copyleft violation. The confirmed, decisive problem is narrower: a publicly-published, "plugin-open" framework whose every non-kernel package is UNLICENSED (granting downstream users zero rights), with no root LICENSE, while its own ADR asserts a different license, cannot make the "plugin-open" premise legally true — a plugin ecosystem cannot form around UNLICENSED packages. Confirmed as a freeze-blocker on this narrower "license coherence for a plugin-open v1" ground (two-key granted).

**F2 — [P2, verifier-downgraded from P1, not freeze-blocking] [verifier: AMENDED]** — `packages/runtime-adapter/src/runtime-adapter.ts:217`, `sandbox-impl.ts:8-11`.
`createMonoRuntime` builds `const hostWithSandbox = { sandbox: monoSandboxImpl, ...hostOptions }` — because `...hostOptions` spreads last, any `sandbox` key present in caller-supplied `hostOptions` silently wins over the injected `monoSandboxImpl`. Neither `CreateMonoRuntimeOptions` nor its parents declare a typed `sandbox` field, but their `readonly [key: string]: unknown` index signature lets one through anyway, and agent-runtime's `HOST_KEYS` reads `"sandbox"` once at construction into the long-lived `ToolContext` — so a collision governs the runtime's entire lifetime, not just one run.
> `const hostWithSandbox = { sandbox: monoSandboxImpl, ...hostOptions } as unknown as KernelHostOptions;`

Verifier amendment: real bug, but latent and low-severity, not "the single most security-relevant seam" in an exploitable sense. No in-repo call site passes a `sandbox` key today (only `sandboxPolicy`/`sandboxEngine`); the kernel's `passthroughSandbox` fails **closed**, so an accidental collision breaks availability, not security; and the threat model is degenerate — only the host author, who already controls the process, can pass options to `createMonoRuntime` in the first place. Downgraded to P2 defense-in-depth hardening; freeze-blocker rejected.

**F3 — [P2] [verifier: CONFIRMED dead]** — `packages/runtime-adapter/src/runtime-helpers.ts:35,62,104,137,154` and `runtime-adapter.ts` (`acceptedSdkIdsForBackend`, `listMonoRuntimeSelectionTable`).
`assertBaseRunOptions`, `readLastStringUserMessage`, `buildRuntimeResult`, `applyTemporaryEnv`, `withTemporaryEnv` are exported through the package's public `index.ts`, documented as shared scaffolding to dedupe "each SDK runtime" (Codex previously kept ~4 byte-identical copies), but are structurally unreachable from the very SDK runtimes they were built for once agent-runtime was split out as a zero-workspace-dependency vendored kernel (agent-runtime importing runtime-adapter would recreate the forbidden cycle). The verifier's proof run confirms all 7 symbols (5 helpers + 2 runtime-adapter exports) resolve to a single hit — the `runtime-adapter/src/index.ts` barrel — across `packages extras demos scripts website docs`, and zero hits in both live instances (`~/personal-agent`, `~/a8c-agents`).

**F4 — [P2, context] [verifier: CONFIRMED, carried forward]** — `packages/runtime-adapter/src/sandbox-managed.ts:245`.
`assertSecureRegularFile`'s blanket `stat.nlink !== 1` rejection matches already-filed, still-open GitHub issue #191 ("Evaluate managed SRT compatibility with hard-linked Node executables") — single-link enforcement is right for the private managed tree but can incorrectly reject a legitimate external Node launcher (NVM/Homebrew/hosted toolcaches) that happens to be hard-linked, since multiple hard links alone don't grant another principal write access. Not a new finding — correctly filed, correctly still open, carried forward for synthesis. Verifier performed no independent check of issue #191's own tracker status (out of read-only file scope) but confirmed the code still matches its description.

**F5 — [P3] [verifier: CONFIRMED]** — `packages/agent-runtime/MIGRATION.md:195-221`.
MIGRATION.md §11 states "3 barrels... plus 21 named deep `.js` subpaths" and enumerates exactly 21, but the actual `package.json` exports map has 22 deep subpaths — `./ai/providers/claude-sdk-discovery.js` works (confirmed via `verify-deep-imports.mjs`) but is missing from the enumerated list. Low severity but this document's whole job is being the authoritative list an external consumer (worklab) reads before porting.

**F6 — [P3/info, correction] [verifier: CONFIRMED as correction]** — package.json exports map.
The recon-hint "76-subpath export surface" does not match reality: the real exports map has 25 entries total (3 barrels + 22 deep `.js` subpaths, per F5), and the full root barrel surfaces 62 distinct named symbols at runtime. Not a defect — the actual surface is smaller than the recon lead suggested — recorded so synthesis doesn't propagate the unverified 76 figure. Of the 22 deep subpaths, only 3 are imported anywhere else in this monorepo today; the rest exist to serve worklab and forward API stability, guarded by `verify-deep-imports.mjs` which — despite appearances — **is** wired into the release gate (`pnpm run test` → `scripts:test` runs a real, non-mocked resolution pass).

**F7 — [P3, cosmetic] [verifier: CONFIRMED]** — `packages/agent-runtime/src/agent/index.js:1-5`.
The vendored kernel's opening doc-comment says "The kernel is consumed by the worker, the assistant, the Slack triage path, and the coordinator's run-spawn path" — none of "the assistant," "Slack triage path," or a bare "worker"/"coordinator" (without the "worklab's coordinator" qualifier used correctly elsewhere, e.g. `ai/failure.js:32`) are mono-agent concepts or identified as belonging to the external worklab host. Recurs across 7 files; only `agent/index.js`'s opening summary gets it wrong. Cosmetic but real against the "competent stranger can understand the core" premise clause.
