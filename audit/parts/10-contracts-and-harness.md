# 10 · agent-contracts & agent-harness kernel

**Scope:** `packages/agent-contracts/src/**` and `packages/agent-harness/src/**` (the dependency-free channel/config/memory contract layer and the turn-orchestration/durable-history harness kernel built on it), plus their READMEs.
**Maturity grade:** B (verifier-adjusted). One P1 correctness finding survives verification but with its blast radius narrowed to a single already-shipped opt-in surface (WhatsApp) rather than three; nothing in this territory is a confirmed freeze-blocker.
**Verdict:** This is careful, well-tested engineering — crash-safe durable history, a genuinely channel-agnostic contract layer, defense-in-depth continuation-capability validation — undercut by one real leak of adapter-specific knowledge into the supposedly channel-neutral harness kernel (a hardcoded `telegram:`/`slack:` prefix check) and a process gap that let it ship without a CI net. The remaining findings are minor legibility and doc-drift items. One originally-reported finding (inert config-version field) was refuted on verification: the field is in fact load-bearing.

## Findings

1. **[P1] [verifier: AMENDED]** — `packages/agent-harness/src/harness.ts:2661-2681`. `sessionContextBlock`'s per-turn "is a live human attached" framing is decided by a hardcoded two-item string-prefix allowlist (`baseId.startsWith("telegram:") || baseId.startsWith("slack:")`) instead of the trigger-metadata signal (`metadata.cron`/`metadata.webhook`) the same function already uses three lines away for the inverse question.
   - Evidence:
     ```ts
     const deliverable = baseId.startsWith("telegram:") || baseId.startsWith("slack:");
     ```
   - Why it matters: violates the premise's "lean, understandable core open to external plugins" — `channel.ts`'s own docstring uses `discord` as the textbook third-party `ChannelId` example, yet the kernel can only recognize two first-party names.
   - **Verifier correction (binding):** the auditor's claim that this misclassifies three shipped surfaces is over-scoped. `openai-api:` is **correctly** classified — the non-interactive framing's own text says "request-driven run (scheduled, webhook, **or API**)" and the OpenAI-API adapter returns synchronously with no push destination to protect. The TUI is **near-harmless** — it streams the reply back synchronously over NDJSON, so "do not invent a callback destination" is operationally correct; only the "no interactive user" wording is cosmetically off. **WhatsApp is the one genuine functional miss**: `extras/whatsapp-adapter/src/adapter.ts:504` builds `whatsapp:${chatJid}`, an async-push channel shaped identically to telegram/slack, and it silently gets told there is no interactive user and no callback destination should be invented. Verifier explicitly rejected this as a freeze-blocker: real bug, but scoped to one extras-tier opt-in channel, not catastrophic, does not falsify "honest ops."

2. **[P2] [verifier: CONFIRMED]** — `scripts/check-package-architecture.mjs:152-160`. The repo's only automated adapter-neutrality guard scans **only** `packages/agent-contracts` (never `packages/agent-harness`, where finding 1 lives) and bans only the literal substrings `"telegram"`/`"whatsapp"` — not `"slack"`, which is also hardcoded in `harness.ts` and separately appears unflagged inside a regex in `agent-contracts/src/tool-hints.ts:24` (`/slack|message|chat|send/u`).
   - Why it matters: the checklist artifact the review process relies on to keep this kernel adapter-neutral cannot catch a leak in `agent-harness` at all, and would not catch a `"slack"` leak even in the one package it does scan. Process gap, not just a code gap.

3. **[P2] [verifier: AMENDED]** — `packages/agent-harness/src/harness.ts` (3,166 lines total). The file mixes at least five separable concerns — turn orchestration (`run()`, ~650 lines), MCP request/continuation-context injection (~350 lines), external-summary redaction (~150 lines), attachment persistence (~150 lines), turn-context event building (~100 lines) — with no submodule boundary, unlike `context/`, `skills/`, and `tool-policy/` next door in the same package.
   - **Verifier correction:** line count (3,166) confirmed exact; the auditor's "70 top-level declarations" figure is imprecise (a declaration-shaped grep actually returns ~104 lines, a mix of true top-level and non-top-level). The substance of the finding — one oversized file straining "understandable core" against the package's own established submodule pattern — stands regardless.

4. **[P3] [verifier: CONFIRMED]** — `packages/agent-contracts/README.md:28`. Documents a Public-API type, `AgentMessageStreamResult`, that does not exist anywhere in `src/` (`grep` returns zero hits; the real stream-result type is `AgentResponse`).
   - Why it matters: undermines "a competent stranger must be able to understand the core" — a reader following the README's own Public API list will not find this type.

5. **[P3] [verifier: CONFIRMED]** — `packages/agent-harness/src/skills/skills.ts:109-115`. Skill-body truncation slices a `Buffer` at a raw byte offset and calls `.toString("utf8")`, which can split a multi-byte character (Node silently emits U+FFFD) — unlike `harness.ts:2956-2969`'s `clampTurnContextText` (and `redaction.ts:100-115`'s `truncateString`) in the same package, both of which walk back past continuation bytes.
   - Why it matters: low impact (the truncation marker already signals the cut), but an avoidable inconsistency for the same class of problem within one package, likely to be missed if fixed in only one place.

6. **[P3, informational] [verifier: NEW]** — `packages/config/src/json-source.ts:220-230` (`readMonoAgentConfigJson`) vs. `packages/agent-contracts/src/json-source.ts` (`writeSettingsJson`/`mergePatch`). Two config-write paths coexist with asymmetric concurrency safety: the conversational proposal path (`agent-app/src/local-configuration.ts`) has full optimistic-concurrency via a `version`/sha-256 CAS token wired through `readMonoAgentConfigJson`; the direct merge path (`writeSettingsJson`, used by channel-adapter config setup and `init`) does an unconditional read-merge-write with no CAS — last-writer-wins.
   - Why it matters: minor and not independently actionable — the direct writers run at setup/init time and are not normally concurrent with the live proposal flow — but noted so this residual asymmetry isn't lost now that the stronger original claim (finding below, refuted) is removed.

## Dead code & deprecation

No dead code was proven in this territory.

- **Suspected (unproven), verifier-resolved to "keep, documented":** `createInMemoryHistoryStore`/`InMemoryConversationHistoryStore` (`packages/agent-harness/src/history.ts`) — exported and README-documented, but the auditor found zero production callers (`configured-agent.ts:430` always defaults to `createDurableHistoryStore`). Verifier confirmed the zero-caller claim (including a grep of both live instances, `~/personal-agent` and `~/a8c-agents`) and confirmed the **keep** disposition: this is a legitimate minimal reference implementation for a third-party embedder of `@mono-agent/agent-harness`, directly serving "lean core open to external plugins." Recommendation: add a README note that no shipped host exercises it end-to-end.

Deprecation/legacy paths in scope — all confirmed **load-bearing, keep** by the verifier, no removal claims made or disputed:
- `LEGACY_STORE_VERSION`/`LEGACY_CONVERSATION_LOCK_PATTERN` (`durable-history.ts:16,36,1610-1611,1825-1858`) — active pre-v2 store/lock migration path.
- `MemoryStore.appendHostSummary`/`scheduleCapture` (`agent-contracts/src/memory.ts:56-67`) — compatibility seam for third-party `MemoryStore` plugins predating the strong-write contract.
- `ConversationHistoryStore.prepareAppend`/`beginProviderSessionTurn` as optional methods (`agent-harness/src/types.ts:56-75`) — plugin seam for custom history stores.
- `skillDisclosure: "full"` (default) vs `"index"` — a first-class current default, not a phase-out path.

**Explicitly refuted — do not resurrect:** the original F3 claimed `ReadSettingsJsonResult.version` (a sha-256 hash) is dead weight with no caller. The verifier found the wrapper `readMonoAgentConfigJson` (`packages/config/src/json-source.ts:220-230`) spreads `version` into `ReadMonoAgentConfigJsonResult`, and `agent-app/src/local-configuration.ts` consumes it as a real optimistic-concurrency/CAS token (`:611`, `:620`, `:662`, `:1446`), rejecting stale proposals with "Configuration changed while the agent was preparing its proposal." **The field is load-bearing — do not delete it.**

## Quarantine (refuted/unproven)

- **Original F3 — `ReadSettingsJsonResult.version` is dead weight, no caller reads it.** **REFUTED.** The auditor grepped only direct `readSettingsJson` consumers and missed the wrapper `readMonoAgentConfigJson` (`packages/config/src/json-source.ts:220-230`), which spreads `version` through, and `agent-app/src/local-configuration.ts`, which consumes it as a real optimistic-concurrency/CAS token at four call sites (`:611`, `:620`, `:662`, `:1446`). The field is load-bearing; do not delete it, and the corresponding actionable step (original C1-3) is withdrawn as moot. A narrower, unestablished residual observation (the *direct* `writeSettingsJson` merge path used by adapter config setup/`init` has no CAS) is preserved above as finding 6 (informational, not independently actionable for v1).
