# 18 · Docs & website

**Scope:** `docs/**` (76 markdown files: playbooks, reference, config, memory, runtime, channels, programmatic, observability, tools) plus the Astro Starlight `website/` build and its CI gate. **Maturity grade:** B+ (verifier-adjusted — grade unchanged, but all three P1 candidate freeze-blockers were rejected on two-key review and downgraded to non-blocking). This is an unusually thorough documentation suite for a v1 — a comprehensive `feature-registry.md`, 15 consistent end-to-end playbooks, and a well-engineered website build with a real link-integrity gate — but verification confirmed a direct self-contradiction in the glossary about memory salience behavior, two shipped/validated config surfaces (`telegram.transcription`, `slack.homeTab`/`slack.shortcuts`) that are invisible outside an auto-generated table, a systemic content-rendering bug (16 empty Starlight callouts), and a playbook code sample that is broken in more ways than originally reported. None of these are functional or security defects in the shipped code itself — they are documentation-accuracy gaps, and the verifier explicitly ruled none of them rise to a freeze-blocking bar.

## Findings

**F1 — [P1] [verifier: CONFIRMED]** — `docs/reference/glossary.md:98-112` — The glossary's "Consolidation" and "Salience" entries describe decay/near-duplicate-superseding behavior that five other authoritative pages explicitly say does **not** happen in v1 (`docs/memory/rituals.md:15-18`, `docs/memory/index.md:44,239`, `docs/memory/backends-comparison.md:95`, `docs/reference/feature-registry.md:81`). This is a direct self-contradiction on a core memory-behavior claim the "clean memory" premise clause depends on operators trusting.
> "A scheduled BuJo maintenance pass... salience decay, near-duplicate superseding..." vs. rituals.md: "salience is static canonical Markdown metadata: scheduled consolidation does not decay it, and it never supersedes..."

**F2 — [P1] [verifier: CONFIRMED]** — `docs/channels/telegram.md` (zero mentions), `docs/config/env-vars.md` (zero mentions) — `telegram.transcription` is a real, shipped, opt-in feature (`packages/telegram-adapter/src/config.ts:280-283`, four env vars) documented only in `feature-registry.md:123`, never on the per-channel setup page a user would actually read, and never in the env-vars page that claims to be "the exhaustive reference." The one parity test that exists (`env-vars-docs-parity.test.ts:110-115`) only asserts coverage for `MONO_AGENT_OPENAI_API_*`, so this exact gap is untested and silent.

**F3 — [P1] [verifier: AMENDED — citations corrected]** — `packages/slack-adapter/src/config.ts:19-49` — `SlackShortcutConfig` and `SlackHomeTabConfig` are real, wired, validated config surfaces with zero prose documentation: not in `docs/channels/slack.md`, `feature-registry.md`, `feature-matrix.md`, or `slack-adapter/README.md`. The only place either appears is the auto-generated field table in `docs/config/reference.md` at **lines 144 & 150** (verifier correction — raw audit cited 275-290). The maintenance rule this violates ("also update its prose page under `docs/<area>/`") lives at **`feature-registry.md:200`** (verifier correction — raw audit cited 189-191, which is the adjacent "not done until it has a row here" rule). Both fields are JSON-only config (`env: "--"`).

**F4 — [P2] [verifier: AMENDED — file count corrected]** — 16 empty Starlight `:::type` / `:::` callout pairs across **11 files** (verifier independently reproduced exactly 16 instances at the auditor's listed file:lines; the raw audit's prose said 13 files, but the enumerated list is 11 — two files each contribute 2 occurrences). Example, `docs/channels/telegram.md:39-42`:
> `:::caution` / `:::` immediately followed by the orphaned caution text as a plain paragraph.

`check-links.mjs` matches only `href`/`src` against the built `dist/` (confirmed at line 35) and cannot catch this class of defect by design. Likely origin: the one-off Jekyll→Starlight migration script mishandling a marker variant.

**F5 — [P2] [verifier: CONFIRMED, and extended by NEW-1]** — `docs/playbooks/multi-agent-orchestration.md:36-43` calls `createCollaboratorToolRuntimeExtension({...})` with no `await` (the function is `async`), omits the required `originalUserMessage`/`abortSignal` fields, and reads `input.conversationId` where the actual callback input shape is `{ request, runId, context }` — the correct path is `input.request.conversationId`. All four defects independently verified against `agent-orchestrator/src/index.ts` and `agent-harness/src/types.ts`.

**F6 — [P2] [verifier: CONFIRMED]** — `website/README.md:27` — the docs-site CI "website" job has no GitHub required-status-check enforcement; a red check is a merge blocker "by convention" only, not a hard gate — and (per F4) it can't even detect content-rot in principle, only link-rot.

**NEW-1 — [P2] [verifier: NEW finding]** — `docs/programmatic/multi-agent.md:85` and `docs/playbooks/multi-agent-orchestration.md:33` both call `createConfiguredAgentResponder({...})` (an `async` function returning `Promise<AgentResponder>`, `configured-agent.ts:533`) with **no `await`**, so `orchestrator` is a Promise and the subsequent `.respond()` call would fail. This extends F5: the reference page the auditor held up as "correct" has its own top-level construction call broken the same way as the playbook it's meant to correct.

## Dead code & deprecation

**Proven dead (tooling, non-urgent):**
- `website/scripts/migrate-callouts.mjs`, `migrate-frontmatter.mjs`, `migrate-links.mjs` — one-off Jekyll/just-the-docs → Starlight conversion scripts. Proof: `grep -rn "migrate-callouts\|migrate-frontmatter\|migrate-links" website/package.json .github/workflows/ci.yml` returns nothing; repo-wide grep (excl. node_modules/dist/audit) shows only a documentation reference in `website/README.md:41-43` (self-disclosed as one-off, "kept for reference"). Verifier confirmed. Tidiness item, not a correctness risk.

No other dead code found in the docs/website scope. The rest of `website/scripts/` (`sync-content.mjs`, `check-links.mjs`) is live and exercised by CI on every push — **explicitly not dead**, do not touch.

**Deprecation classifications — all confirmed sound (no false "removable-now" claims):**
- `mono-agent recipes` → alias of `presets`, and `--recipe` flags — documented forward-mapping table, load-bearing, not removable.
- Legacy snake_case tool names (`slack_send_message`, `telegram_ask`, etc.) — documented deprecated aliases, load-bearing, not removable.
- `runtime.fallbackModels` / `MONO_AGENT_FALLBACK_MODELS` — documented legacy form, load-bearing, not removable.
- `memory.reflection.*` / `memory.migration.*` — tolerated-but-ignored with a validate warning, correctly classified, not removable (breaking stale-environment startup would be worse).
- `@mono-agent/memory-mcp` — already fully retired; docs give accurate three-path migration guidance.
- `@mono-agent/operator-console` — retired per PR #28; verifier and auditor both confirm zero stale references anywhere in `docs/**`. Not a finding.

## Quarantine (refuted/unproven)

None of this territory's findings were refuted outright — F1 through F6, NEW-1, and the dead-code entry all survived verification (F3 and F4 with citation/count corrections applied above, not rejections). The only downgrades were on the freeze-blocking axis, not on the underlying substance:

- **E1-1, E1-2, E1-3 freeze-blocker candidacy — REJECTED by verifier (two-key rule).** The raw audit's DoD table marked these `y` (freeze-blocking); the verifier explicitly rejected all three, reasoning: "the freeze bar is 'blocks a DoD clause / secret-license-correctness catastrophe / makes honest ops false.' All three are documentation defects on surfaces whose *code* is correct and shipping." They remain strong P1s for the pre-freeze doc-sweep but do not halt the freeze.
