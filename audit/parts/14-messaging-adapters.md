# 14 · Messaging adapters (Telegram & Slack)

**Scope:** `packages/telegram-adapter` and `packages/slack-adapter` — config loading, long-poll/socket-mode reliability loops, interaction features (ask-buttons, reactions, shortcuts/Home-tab), notification/redaction plumbing, and both packages' READMEs.

**Maturity grade:** B+ (verifier-adjusted; no changes to the raw grade — the verifier upheld it). Both adapters are mature, carefully-reasoned engineering with real fake-timer tests exercising the exact failure modes they claim to handle (10,426 lines of tests across the two packages). The verifier independently accepted the auditor's account of PR #243 (raising the `getUpdates` runner retry budget from 15s to 90s, kept under the 120s poll-liveness watchdog, plus a same-runner-generation recovery check) as a real, tested, root-caused fix — not config tuning or a band-aid. The one recurring defect — structural JSON config validated *before* the `enabled` early-out, identically in both adapters — was confirmed as a real P1 bug but explicitly rejected as a freeze-blocker under the two-key rule: it fails loudly and names the offending field (honest, not dishonest), the trigger is narrow (malformed advanced structural block + disabled channel), and no v1 DoD clause requires disabled channels to skip structural validation.

## Findings

**F1 — [P1] [verifier: CONFIRMED] — Disabled-channel structural config is still hard-validated, contradicting the adapters' own documented invariant, in both adapters.**
`packages/telegram-adapter/src/config.ts:185` — `readTelegramSendTools(json)` runs before the `if (!enabled)` early-out at `:190`, so a malformed `telegram.sendTools` block (unknown field, or `scope` set to something other than `"producing-conversation"`) throws a hard `TelegramAdapterConfigError` even when `telegram.enabled` is `false`. This contradicts the comment two lines above the early-out: *"A disabled channel never validates its credentials: the status surface reads it as 'disabled', not 'waiting for config'."* Every other structural field in the same function (`quietHours`, `commands`, `reactions`, `apiRoot`, `attachments`, `transcription`) is read only after the enabled check. The identical bug shape exists in Slack: `packages/slack-adapter/src/config.ts:149-150` — `readSlackShortcuts(json)`/`readSlackHomeTab(json)` both run before the `enabled` read (`:151`) and the early-out (`:171`).
Why it matters: the premise promises "agents in seconds-to-minutes" and "honest ops." A user who disables a channel to sidestep a config problem — a natural workflow step — can instead find `mono-agent validate`/`doctor` still hard-fails, with no indication the failing block belongs to a channel just turned off. `config.test.ts` for both packages only exercises "disabled + empty config," never "disabled + malformed structural block."
Verifier evidence: confirmed both `readTelegramSendTools` (`:246-262`) and `readSlackShortcuts`/`readSlackHomeTab` (`:273`, `:335`) throw on malformed input; "doubled + documented-invariant violation" upheld the P1 severity. Freeze-blocker explicitly rejected — see Actionable steps and Quarantine below.

**F2 — [P2] [verifier: CONFIRMED] — READMEs advertise a public-API symbol that no longer exists.**
`packages/telegram-adapter/README.md:44,55` and `packages/slack-adapter/README.md:36` show `telegramFieldGroup`/`slackFieldGroup` as importable/public API. Neither symbol is exported by the current `index.ts` (`telegram-adapter/src/index.ts:103-121`, `slack-adapter/src/index.ts:99-114`) — both were renamed to `TELEGRAM_CONFIG_FIELDS`/`SLACK_CONFIG_FIELDS` during the config-consolidation work and are the names actually consumed downstream (`agent-app/src/config-reference.ts:22-23,42-43`, `agent-app/src/channels.ts:229,370`). Copy-pasting the README's own usage example would fail at import time.
Why it matters: the premise wants "a lean, understandable core open to external plugins" — the README is the first thing an external integrator reads, and it is factually wrong about the package's own public surface.
Verifier evidence: `grep FieldGroup packages/*/src/index.ts` returns nothing; actual exports confirmed at `index.ts:107`/`:102`. Recurring pattern noted across C5 + C6 (webhook/cron/openai READMEs share the same stale-`*FieldGroup` trace back to one deleted registry).

**F3 — [P2] [verifier: CONFIRMED] — `showThoughts` is a fully dead, no-op configuration field threaded through the entire Telegram stack.**
Declared and forwarded at `telegram-adapter/src/adapter.ts:190` (`TelegramAdapterStreamOptions.showThoughts`), `bot.ts:1255-1256`, and `message-stream.ts:49` — but the `TelegramMessageStream` constructor (`message-stream.ts:252-307`) never reads `options.showThoughts` when building the inner `ResilientMessageStream` options; it is silently dropped. `agent-app/src/channels.ts:1440` unconditionally sets `showThoughts: true` in the live stream config for every Telegram agent, believing it does something. Slack's equivalent `SlackAdapterStreamOptions` (`slack-adapter/src/adapter.ts:147-160`) has no such field at all — it was correctly dropped there.
Why it matters: a config knob that is documented ("Retained for compatibility... this is a no-op") but still fully wired end-to-end, including a hard-coded call site believing it's live, is exactly the kind of leaky abstraction that erodes "a lean, understandable core."
Verifier evidence: confirmed the constructor reads `maxMessageChars`/`formatMarkdown`/`initialStatusText`/`editDebounceMs`/... but never `showThoughts`; 5 total hits repo-wide (2 type decls, 1 forward, 1 app set-true, 0 reads).

**F4 — [P3] [verifier: CONFIRMED] — `redactSlackAdapterConfig` is dead exported code; its Telegram sibling is a second, hand-maintained redaction path that has already drifted from the app's real config-provenance mechanism.**
`slack-adapter/src/config.ts:432-449` defines and `index.ts:99-104` exports `redactSlackAdapterConfig`; a repo-wide search finds zero production or demo consumers. Its Telegram counterpart `redactTelegramAdapterConfig` (`telegram-adapter/src/config.ts:605-624`) has exactly one consumer: `demos/final-agent/src/configuration.ts:19,58`. The real production host (`agent-app`) redacts channel config through a completely different, generic mechanism (`buildChannelConfigView` + `TELEGRAM_CONFIG_FIELDS`/`SLACK_CONFIG_FIELDS`, `agent-app/src/channels.ts:229,370`, `config-reference.ts:22-43`) with its own `secret: true` markers per field.
Why it matters: two independently-maintained redaction paths for the same config shape is a duplication risk — a newly-added secret field could be added to `TELEGRAM_CONFIG_FIELDS`/`SLACK_CONFIG_FIELDS` (used by the real app) without a matching update to the adapter's own hand-rolled redactor (used only by a demo, or by nothing).
Verifier evidence: `grep -rn redactSlackAdapterConfig` repo-wide → only definition, export, and self-test. "Drift risk is real but low."

**F5 — [P3] [verifier: CONFIRMED] — Slack has no quiet-hours/silent-delivery parity with Telegram.**
Telegram's config surface (`telegram-adapter/src/config.ts:28-32,504-565`) defines `TelegramQuietHours`/`isWithinQuietHours`, and its notify/stream plumbing (`bot.ts:145-152`, `message-stream.ts:63-66`) carries a `silent` flag end-to-end. Slack's `SlackNotifyOptions` (`slack-adapter/src/adapter.ts:121-125`) has only `verbatim` and `deliveryKey` — no `silent` concept anywhere in `slack-adapter/src`. A cron/webhook quiet-hours policy therefore cannot be honored uniformly across channels from inside these packages.
Why it matters: "channels easily" implies parity — an operator configuring a proactive-notification policy should not need to know it silently does nothing on one of the two flagship channels.
Verifier evidence: `grep silent|quietHours|disable_notification slack-adapter/src` → every "silent" hit is about a silently-dead socket (`start.ts:66`, `socket-mode-runner.ts:77,424,440`), none is a notify flag — confirming no false negative in the original finding.

**F6 — [P3] [verifier: CONFIRMED] — Slack's error-text is a plain string; Telegram's supports a computed callback.**
`TelegramAdapterErrorText` (`telegram-adapter/src/adapter.ts:174-181`) is `string | ((input) => string | Promise<string>)`, resolved via `resolveErrorText` (`adapter.ts:908-934`) with a documented empty-result/callback-throw fallback. `SlackAdapterMessages.errorText` (`slack-adapter/src/adapter.ts:143`) is `string` only, and `respondToEvent` (`adapter.ts:1408-1412`) uses it verbatim with no equivalent extension point. Minor asymmetry between the two "flagship" channels.

**F7 — [P3] [verifier: CONFIRMED] — Slack has no analog of Telegram's secret-redaction module.**
Telegram ships a 348-line dedicated module (`telegram-adapter/src/log-redaction.ts`) that deep-sanitizes arbitrary log values/errors (token patterns, bearer/auth headers, query-string secrets, nested `cause` chains, circular-reference guards) before anything reaches a logger. Slack has nothing comparable: `slack-client.ts` and `adapter.ts` log with plain `error instanceof Error ? error.message : String(error)` (e.g. `adapter.ts:1252-1255,1280-1283`) and construct `SlackApiError` without embedding the bot/app token in `message` today — no active leak, but no defense-in-depth if a future change starts logging a raw response/fetch error object carrying request headers.
Verifier evidence: accepted as-is; "no active leak today, defense-in-depth parity gap."

**PR #243 focus-question validation (verifier-accepted, not a finding):** the auditor's account that #243 fixed the `getUpdates` timeout→restart loop is ACCEPTED by the verifier as internally consistent and backed by named tests (`start.test.ts:173,571,775,940`) — raising the runner's retry budget 15s→90s, kept under the 120s poll-liveness watchdog, and requiring a real successful `getUpdates` from the same runner generation before declaring recovery. Not independently re-derived, but no red flags raised.

## Dead code & deprecation

Proven dead (grep-verified by the adversarial pass, repo-wide excluding `node_modules`/`dist`):

- **`showThoughts`** (`telegram-adapter/src/adapter.ts:190`, `bot.ts:1255-1256`, `message-stream.ts:49`) — threaded through 3 declare/forward sites plus one app call site (`agent-app/src/channels.ts:1440` hard-codes `showThoughts: true`), but never read by `TelegramMessageStream`'s constructor (`message-stream.ts:252-307`, read in full and confirmed absent). Proof: `grep -rn showThoughts packages --include=*.ts` (excl. tests/dist) → 5 hits, no read site.
- **`redactSlackAdapterConfig`** (`slack-adapter/src/config.ts:432-449`, exported at `index.ts:99-104`) — zero consumers outside `slack-adapter/` itself. Proof: `grep -rln redactSlackAdapterConfig` repo-wide → only the definition, its export, and its own unit test.

No entries were refuted as non-dead by the verifier for this territory.

**Deprecation:** none in scope — no `@deprecated` (or textually "deprecated") markers anywhere in `packages/telegram-adapter/src` or `packages/slack-adapter/src`. The `showThoughts` field is soft-deprecated-in-JSDoc ("Retained for compatibility... a no-op") but never formally scheduled for removal — folded into the dead-code entry above per the verifier.

## Quarantine (refuted/unproven)

No findings in this territory were refuted by the verifier — all 7 findings and both dead-code claims were CONFIRMED. The only downgrades applied were to the **freeze-blocking status** of two actionable steps, kept here for auditability:

- **C5-1 (freeze-blocker proposal) — REJECTED.** Telegram `sendTools` validated before the `enabled` early-out fails loudly and names the offending field (honest, not a silent/dishonest failure path); the trigger is narrow (malformed *advanced* structural block AND channel disabled simultaneously); no v1 DoD clause requires disabled channels to skip structural validation; not a correctness/secret/license catastrophe. Remains a real P1 finding worth fixing pre-freeze, just not a blocker.
- **C5-2 (freeze-blocker proposal) — REJECTED.** Identical reasoning to C5-1, applied to the sibling Slack `shortcuts`/`homeTab` bug.
