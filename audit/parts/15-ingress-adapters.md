# 15 · Ingress adapters (webhook, cron, openai-api, operator)

**Scope:** `packages/webhook-adapter`, `packages/cron-adapter`, `packages/openai-api-adapter`, `packages/operator-adapter` (tui + live sub-adapters) — source and READMEs only, no live-instance scope.

**Maturity grade:** B- (verifier-adjusted). All four packages are small, dependency-clean, and share a consistent, well-tested `AgentResponder`/`AgentMessageStream` structural pattern with real defensive engineering (graceful-abort watchdogs, per-run isolation, prototype-pollution-safe metadata sanitization). Real `vitest --coverage` runs refute the recon's low-coverage hints for operator-adapter/openai-api-adapter — all four packages sit at 81.76%–90.17% statement coverage. The verifier confirmed 9 of 10 findings as-stated and amended the tenth (the cron README/overlap contradiction) from P1 to P2 after discovering the feature is unreachable from the mono-agent product config surface — no freeze-blocker survives in this part. The grade is held down by a cluster of P2 documentation, parity, and coverage gaps repeated across siblings, none individually severe but collectively indicating the four adapters were built independently rather than to one shared checklist.

Per-package grades (unchanged by verification): webhook-adapter B+, cron-adapter B- (docs debt, strong code), openai-api-adapter B+, operator-adapter B- (weakest real coverage, missing config test for `live/`).

## Findings

**F1 [P2 after verification] [verifier: AMENDED]** — `packages/cron-adapter/README.md:34,87` vs `packages/cron-adapter/src/scheduler.ts:55`.
The README says overlapping cron runs are "skipped, not queued or run concurrently" and explicitly claims the package "does not... queue overlapping jobs," but `scheduler.ts:55` defines a fully implemented `CronOverlapMode = "queue" | "skip" | "replace"` with `maxQueueDepth`/`overflow` policy (`scheduler.ts:282-362`), tested at `cron-adapter.test.ts:223,296,347,416,551`. Originally rated P1 (documentation directly contradicting a shipped, tested feature — violates the "crons... easily" and core-legibility clauses). The verifier **downgraded to P2 and rejected it as a freeze-blocker**: `CronJobConfig` (`config.ts:17-32`) has no `overlap` field, the config loader/`jobs-dir.ts`/`toCronJobs()` never parse or project one, and `agent-app/src/channels.ts:1057-1063` **hardcodes `overlap:"skip"`** with an explicit comment that queue/replace remain available only to programmatic callers of `startCronAdapter`. For every mono-agent product user, cron IS skip-only, and `docs/channels/cron.md:126-131` is honest for that audience. The bug is real but confined to the low-level package README misdescribing its programmatic API for direct embedders (who see the true API via TS types regardless). See F11 (verifier NEW-1) for the reframed underlying issue.
```
Overlapping runs for the same job are skipped, not queued or run concurrently.
```

**F2 [P2] [verifier: CONFIRMED]** — `packages/openai-api-adapter/src/server.ts:307-323` vs `webhook-adapter/src/server.ts`, `operator-adapter/src/tui/server.ts`, `operator-adapter/src/live/server.ts`.
Only openai-api-adapter re-validates the actual OS-resolved bind address after `listen()` resolves; its three siblings call `assertSafeBind` pre-listen (webhook `:246`, live `:84`, tui `:107`) but never re-check `address.address` afterward. This defends against the OS resolving a configured host string to an unexpected concrete address after the pre-bind string check already passed — a genuine, cheaply-fixable safety asymmetry across four otherwise-consistent sibling HTTP adapters.

```ts
const boundNonLoopback = !isLoopbackHost(address.address);
if (boundNonLoopback && options.allowNonLoopback !== true) {
  await closeRejectedServer();
  throw new OpenAIApiAdapterError("unsafe_host", ...
```

**F3 [P2] [verifier: CONFIRMED]** — `packages/cron-adapter/src/config.ts:167-172`, exported `index.ts:28`.
`toCronJobs()` is a safety-critical, footgun-guarded public function ("Hosts must route config jobs through this rather than spreading them directly, otherwise the `enabled` flag is silently ignored and disabled jobs would run") that is entirely absent from the README's Public API list (lines 69-79). Verifier confirmed via `grep toCronJobs cron-adapter/README.md` returning nothing. A reader who only skims the README — the primary onboarding path per the premise — would not learn the function exists, let alone that skipping it silently runs disabled jobs.

**F4 [P2] [verifier: CONFIRMED]** — `packages/openai-api-adapter/src/server.ts:978-996` (`readParameters`).
OpenAI sampling parameters (`temperature`, `top_p`, `max_tokens`, `stop`, `seed`, `logit_bias`, `presence_penalty`, `frequency_penalty`) are extracted into `metadata.openaiApi.parameters` on every chat request but never consumed anywhere in `agent-app` or `agent-harness`. Verifier's own grep (`temperature` across non-test `packages/*/src`, and `.parameters` in `agent-app`/`agent-harness`) confirms zero consumers. An OpenWebUI user adjusting a sampling slider gets a `200 OK` with the value silently discarded — no error, warning, or documented caveat. A genuine "honest ops" gap.

**F5 [P2] [verifier: CONFIRMED]** — `packages/operator-adapter/src/live/__tests__/` (only `server.test.ts`) vs `packages/operator-adapter/src/tui/__tests__/config.test.ts`.
`live/config.ts` has zero dedicated tests, unlike every sibling config module (tui, openai-api, webhook all have one). The only touch point is a `typeof`-only check in `public-api.test.ts:27-28`, never invoked with real data. `redactLiveAdapterConfig` (`live/config.ts:72-81`) exists specifically to keep an `apiKey` secret out of config-view output, and that exact call site is untested — real coverage confirms lines 73-81 uncovered (84.37% file coverage). Verifier confirmed the asymmetry via directory listing and coverage figures.

**F6 [P2] [verifier: PLAUSIBLE — not independently line-verified]** — `packages/openai-api-adapter/src/server.ts:1069-1097` (`openWebUIToolDetails`) vs `packages/operator-adapter/src/tui/server.ts:301-343` (`truncateEvent`).
The auditor's claim is that openai-api-adapter's SSE tool-call rendering embeds a tool call's raw `arguments`/`result` into an HTML `<details>` block with no size limit, unlike the TUI adapter's `MAX_FRAME_BYTES`-bounded truncation for the equivalent NDJSON frame. The verifier judged this consistent with the codebase's general shape but did not line-verify `server.ts:1069-1097` in its pass, marking it PLAUSIBLE rather than CONFIRMED, and noted low blast radius since openai-api-adapter is loopback-default. Treat as a real but unconfirmed-in-detail asymmetry.

**F7 [P3] [verifier: CONFIRMED]** — `packages/webhook-adapter/README.md:82`, `packages/cron-adapter/README.md:78`, `packages/openai-api-adapter/README.md:96`.
All three READMEs advertise a `*FieldGroup` export (`webhookFieldGroup`, `cronFieldGroup`, `openAIApiFieldGroup`) that does not exist in any package's `src/`. Verifier confirmed via grep in each `src/index.ts` (none) — leftover doc debris from the deleted zero-consumer field-group registry (per user memory `config-consolidation-recipes.md`). `operator-adapter/README.md` correctly has no such reference. This is part of a cross-cluster pattern also found in C5 (telegram/slack), traced to the same deleted registry.

**F8 [P3] [verifier: CONFIRMED]** — `packages/webhook-adapter/src/server.ts:835-837`, `packages/agent-app/src/channels.ts:1000-1001`, `packages/agent-harness/src/harness.ts:2667` (latter two out of this part's file scope).
The `telegram:`/`slack:` deliverable-conversation check (`isDeliverableConversation`) is triplicated verbatim across three packages with no shared constant/helper. Verifier proved three identical copies exist and no shared helper backs any of them. Flagged cross-cluster for the C1/C2 verifier to own the de-dup action once, at the right package.

**F9 [P3] [verifier: CONFIRMED]** — `packages/webhook-adapter/src/server.ts` (`WebhookAdapterOptions` lines 126-149, `config.ts:35-49`).
webhook-adapter is the only HTTP-bearing sibling with no built-in `apiKey`/bearer-auth option, unlike openai-api-adapter, tui, and live (all support an optional bearer key via `bearerTokensEqual`). Honestly disclosed in `webhook-adapter/README.md:91` and `docs/channels/webhook.md:57` ("put it behind a reverse proxy or auth layer you control"), but webhook is, by nature, the adapter most likely to need real non-loopback exposure for third-party provider callbacks, making the missing built-in option a real defense-in-depth inconsistency.

**F10 [P3] [verifier: CONFIRMED]** — `packages/webhook-adapter/src/server.ts:132-138,463` vs `packages/cron-adapter/src/scheduler.ts:35-36,429`.
webhook-adapter has only a single adapter-wide `maxRunMs` shared by every endpoint's watchdog, while cron-adapter gives each job its own optional `maxRunMs` with a shared fallback (`job.maxRunMs ?? options.maxRunMs`). The webhook README claims the watchdog "mirrors the cron adapter," but the per-job/per-endpoint override parity is incomplete — endpoints sharing one server cannot get different watchdog bounds today.

**F11 [P3, reframes F1] [verifier: NEW]** — `packages/cron-adapter/src/config.ts` (no `overlap` field), `packages/agent-app/src/channels.ts:1057-1063`.
The verifier's NEW-1 finding: the cron `overlap:"queue"/"replace"` + `maxQueueDepth`/`overflow` machinery (`scheduler.ts:282-362`) is fully built and tested but **unreachable from the mono-agent product config surface**. `CronJobConfig` has no overlap field; the config loader, `jobs-dir.ts`, and `toCronJobs()` never parse or project it; `agent-app/src/channels.ts:1057-1063` hardcodes `overlap:"skip"` with a comment noting queue/replace remain available only to programmatic callers. This explains and supersedes F1's severity: `docs/channels/cron.md:126-131` is legitimately honest for the config-file audience. For the v1-freeze "lean core" lens, this is a product decision point — whether an unreachable-from-config feature belongs in the frozen surface, or should be documented purely as an embedder-only API.

## Dead code & deprecation

**Proven: none found in this part's `src/` trees.** Every exported function traces to either a real call site or a test; the verifier confirmed the auditor's ruled-out candidates as reasonable:

- `handleTick` (`cron-adapter/scheduler.ts:282`) — deliberately internal-only, imported directly by `cron-adapter.test.ts:9` for regression testing. Not dead. Verifier confirmed via re-check of the import.
- `CronJobConfig.notifyFailureCooldownHours` — validated/parsed in `config.ts`/`jobs-dir.ts` but intentionally not projected by `toCronJobs()`; read directly off the retained `CronJobConfig[]` by `agent-app/src/channels.ts:1143` for host-side cooldown logic. Verifier confirmed this read site. Not dead.
- `RedactedWebhookAdapterConfig`/`RedactedCronAdapterConfig` — identity-transform types, an intentional consequence of a uniform `redact*Config` pattern applied across every channel adapter (these two configs hold no secrets). Not dead.

No `@deprecated` JSDoc tags exist in this part's scope. The single-endpoint/single-job legacy config shapes (`webhook-adapter/src/config.ts:121`, `server.ts:141,145,785`; `cron-adapter/src/scheduler.ts:51,298` default `overlap:"skip"`) are the primary on-ramp most simple agent configs still use and are actively exercised by tests — **load-bearing, not deprecated for removal.** The verifier confirmed this classification without amendment.

Suspected (unproven): none — the auditor's investigation in this part reached firm dispositions on every candidate, and the verifier did not surface any additional suspects.
