# 19 · Scripts, CI & Release Lane

**Scope:** `scripts/*.mjs`, `scripts/release/**`, `scripts/__tests__/**`, `.github/workflows/**`, `.githooks`, `.gitleaks.toml`, `pnpm-workspace.yaml`, root `package.json`, `CHANGELOG.md`.

**Maturity grade: C+ (verifier-adjusted, unchanged).** The engineering craftsmanship here is genuinely strong — fail-closed provenance checks, TOCTOU-closing double-reads, honest issue-tracking of known gaps, and an npm release history that matches CHANGELOG.md exactly. But the one artifact this territory exists to produce — a trustworthy "is v1 ready to freeze" signal — has a real, verifier-confirmed gap: the v1 freeze DoD's 7-consecutive-green-days clause is unmet, there is no daily automation currently running it, and (per the verifier's own re-check) a temporary tracker that *had* been running was deliberately unloaded on 2026-07-13 with an operator comment stating the condition did not pass. The verifier also found the fleet's last recorded green check ran against a sha two commits behind current HEAD, meaning the 7-day window cannot even begin until a freeze commit is chosen and redeployed.

## Findings

**F1 [P0] [verifier: AMENDED]** — `scripts/fleet-green-check.mjs:39-40`, `skills/fleet-deploy/SKILL.md:153-155`
The v1 freeze DoD's sole "7 consecutive green days" mechanism has no daily automation currently running, and the operator's own record shows the counter has already failed to complete a window.
Why it matters: the epic's stated closing condition ("Fleet validates and runs green for 7 consecutive days on the v1 build") depends on this script running unattended every day; without that, the DoD cannot be honestly claimed.
Verifier correction to the original framing: the raw audit's claim of "zero comments for 2026-07-13 and 2026-07-14" is **false for 07-13** — there IS a 07-13 comment, an explicit operator cancellation marker ("The seven-consecutive-day condition did not pass… temporary 21:00 tracker was unloaded before its next run"). A temporary launchd tracker *did* exist and produced the daily comments from 07-08 through 07-12, and was deliberately unloaded — so `SKILL.md`'s "installed nightly job" language was true temporarily, now stale, not "never installed." Net effect: the underlying defect (no live automation today, DoD clause unmet) is CONFIRMED and the severity stays P0; only the "was it ever installed" framing was wrong.
Evidence:
> "The seven-consecutive-day condition did not pass… temporary 21:00 tracker was unloaded before its next run" (issue #119, 2026-07-13 comment)

**F1a [P0, folds into F1] [verifier: NEW-1]** — fleet deploy sha vs. HEAD
The only green-check on record (2026-07-15) reports `Deployed sha: 4ebd8e0`, the v0.11.1 merge commit, which is **2 commits behind** current HEAD `5f27a0ec` (`git log 4ebd8e02..5f27a0ec` = 2 commits). The 7-day clock cannot even start on the actual freeze build until the fleet is redeployed to the chosen freeze sha.
Why it matters: even once daily automation exists, the window must run against the correct commit, or the "green for 7 days on the v1 build" clause is measuring the wrong thing.
Evidence: `git log 4ebd8e02..5f27a0ec` → 2 commits (`218ec3bd`, `5f27a0ec`).

**F2 [P1] [verifier: CONFIRMED]** — `scripts/verify-all.mjs:8-19,63-78`, `.github/workflows/ci.yml:44-93`
`pnpm run verify:all` and CI each run checks the other doesn't, in both directions; the gap that matters most is untested in CI at all. `verify-all.mjs` never calls `release:validate`/`release:pack`/`release:consumer`; CI (`ci.yml:65,74,78`) runs those but never `verify:consumers` — grep confirms zero references to `verify:consumers`/`verify-consumers.mjs` anywhere in `.github/workflows/*.yml`.
Why it matters: the consumer-contract fixtures are precisely the check that validates the "config-first, agent-in-seconds" premise end-to-end; a regression there can merge on green CI and is caught only if a human separately runs `verify:all`. `skills/verify-green/SKILL.md` (verifier corrects the cite from lines 15-17 to line 24) calls `verify:all` a "one-shot equivalent" of CI — overstated in both directions.
Evidence:
> grep -n "verify:consumers\|verify-consumers" .github/workflows/ → empty

**F3 [P2] [verifier: CONFIRMED]** — `package.json:13,23-25`, `.github/workflows/ci.yml:86-93`, `scripts/verify-all.mjs:17`
CI re-runs the demo build/typecheck/test after they've already run once via `package.json`'s own script chaining (`build`→`build:demo`, `typecheck`→`typecheck:demo`, `test`→`test:demo`). `verify-all.mjs:17` has the same redundant `test:demo` entry. Verifier notes the "three separate times" framing is slightly loose (it's 3 commands each doubled, not tripled) but the substance holds.
Why it matters: wastes real CI minutes on identical re-execution, and the redundancy is invisible to anyone reading `ci.yml` because it's hidden inside `package.json`'s chaining.
Evidence: `build-with-provenance.mjs:31-34` `BUILD_COMMANDS` already chains `build:demo`.

**F4 [P2] [verifier: CONFIRMED]** — `scripts/check-getting-started-version-pins.mjs:90-108`, `scripts/verify-deep-imports.mjs:12-14`
Two real checks are "phantom gates": exercised only because a test happens to call the real function with no mocks, not because any named `package.json` script or CI/`verify-all.mjs` step runs them. `check-getting-started-version-pins.mjs` has a full `main()`/CLI entry but no `check:getting-started-version-pins` entry anywhere; it runs only via `getting-started-version-pins.test.mjs:6-9`'s no-override call, by accident of the `scripts:test` glob. `verify-deep-imports.mjs` self-declares "part of the phase gate" in its own header comment but is likewise absent from `verify-all.mjs`, `package.json`, and both workflow files (independently confirmed by the C2 auditor too).
Why it matters: a future edit to the `scripts:test` glob or to either test's mocking discipline would silently remove real protection with no named CI step to point at as broken.
Evidence: `grep "getting-started-version-pins\|verify-deep-imports\|check:deep-imports" package.json verify-all.mjs .github/workflows/` → empty.

**F5 [P2] [verifier: CONFIRMED]** — `scripts/release/validate-release.mjs:36-100`
`validateRelease` reads `rootPackageJson` (line 39) but only for the `engines.node` check; the internal-dependency-pin loop (lines 82-94) iterates the discovered publishable packages, never the root manifest's own 18 `@mono-agent/*` devDependency pins (all currently `workspace:0.11.2`). Already tracked by open issue #228 (opened from the v0.8.0 release review); disposition confirmed accurate as of HEAD `5f27a0ec`.
Why it matters: a stale root pin on a future release would pass `validateRelease`/CI/`verify:all` silently.
Evidence: root has 18 `@mono-agent/*` devDeps, all `workspace:0.11.2` (verifier's independent `node -e` count).

**F6 [P2] [verifier: CONFIRMED]** — `scripts/fleet-green-check.mjs` (2,380 lines, ~84-90 functions)
A single-file legibility outlier even for an ops/audit tool — no other in-territory script exceeds 900 lines. Dense near-duplicate guard clauses repeat roughly a dozen times across `evaluateLoaded` (lines 554-774). Verifier caveat for synthesis: this is an ops/audit script, not the runtime "core" that the "competent-stranger-reads-the-core" premise clause centers on — apply the clause with that framing. It is heavily unit-tested (123 assertions across 17 `describe` blocks), so correctness risk is mitigated; this is a legibility/maintainability finding, not a correctness one.
Evidence: `wc -l` = 2380 exactly; verifier's independent function-count grep ≈ 84 (auditor's "~90" close).

**F7 [P3, confirmed-accurate, no action needed] [verifier: CONFIRMED]** — issues #226, #230
Two already-tracked, honestly-disclosed release/provenance limitations, re-verified against current code: #226 (hardcoded `/usr/bin/git` trusted path + Windows-descendant-of-Node constraint in `build-with-provenance.mjs`, explicitly scoped as non-blocking for the current macOS fleet) and #230 (no npm OIDC/trusted-publishing provenance; single combined packed-consumer fixture). Additional minor observation: each release leaves a permanent `mono-agent-stage-<version>` npm dist-tag behind that nothing prunes (7 accumulated since 0.8.0) — cosmetic registry hygiene debt, P3.
Evidence: `build-with-provenance.mjs:29` `TRUSTED_GIT = "/usr/bin/git"`, re-verified present exactly as described.
