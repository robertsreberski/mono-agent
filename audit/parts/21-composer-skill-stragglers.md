# 21 · Composer skill, srt resource, scripts/lib & root workspace-config stragglers

**Scope:** `mono-agent-composer` skill (`packages/agent-app/skills/mono-agent-composer/**`), the SRT resource package, `scripts/lib/*.mjs` build/calibration tooling, and root workspace configs (`vitest.config.mjs`, `website/pnpm-workspace.yaml`).
**Maturity grade:** C+ (verifier-adjusted; matches raw grade — the verifier CONFIRMED the substance of every drift finding while rejecting the freeze-blocking framing). The composer skill is well-written and mostly accurate against v0.11.2 (CLI flags, presets, sandbox semantics, effort clamping, package-boundary rules all check out), but its central premise — that `references/*.md` are "complete" and that absence from the tables means "not configurable, never go check the source" — is false for at least six shipped, config-only features, and the verifier found three more on top. The other scope items (SRT integrity lock, `scripts/lib` build/calibration tooling, root workspace configs) are clean: no dead code, no drift.

## Findings

1. **[P1] [verifier: CONFIRMED]** — native cron/webhook `notify` feature entirely missing from composer references. `references/feature-coverage.md` (self-described "authoritative, exhaustive") and `references/config-blueprint.md`'s annotated `cron`/`webhook` sections never mention `notify`, `notifyConversationId`, or `notifyFailureCooldownHours`, though these are real shipped fields wired through `CRON_CONFIG_FIELDS`/`WEBHOOK_CONFIG_FIELDS` and documented at `docs/reference/feature-registry.md:134` (`channel.native-notify`). Per `SKILL.md:16`, absence from the table means "not configurable" — a user asking for a cron digest gets steered to the superseded tool-call pattern instead of the canonical `notify: true`.
   ```
   packages/cron-adapter/src/config.ts:25-28
     readonly notify?: boolean;
     readonly notifyConversationId?: string;
     readonly notifyFailureCooldownHours?: number;
   ```

2. **[P1, borderline P1/P2] [verifier: AMENDED]** — `playbooks.md` playbook 6 teaches the superseded pre-notify pattern, contradicting its own "mirrors the published Playbooks index" claim. The canonical `docs/playbooks/cron-digest-proactive-notify.md` is built entirely around `notify: true`/`notifyConversationId` with no tool call; the composer's mirrored playbook 6 still uses `"allowedTools": ["SlackSendMessage", ...]` with a prompt to post "via SlackSendMessage." **Verifier correction:** the taught config still *functions* (`SlackSendMessage` is a current, valid adapter-send tool used legitimately elsewhere, e.g. playbook 2) — this is a stale/worse-pattern quality gap, not a broken config or reference to a deleted symbol. P1 is defensible on the false "mirrors" claim; P2 on functional impact.

3. **[P1] [verifier: CONFIRMED]** — `runtime.per-trigger-model` (per-cron-job / per-webhook-endpoint `model`/`effort` override) undocumented in the composer skill. Real fields at `cron-adapter/src/config.ts:29-32` and `webhook-adapter/src/config.ts:29-32`, wired through `CRON_CONFIG_FIELDS:267-268`/`WEBHOOK_CONFIG_FIELDS:311-312`, documented at `docs/reference/feature-registry.md:135`. Neither `feature-coverage.md`'s Channels table nor `config-blueprint.md`'s annotated `cron`/`webhook` blocks mention job/endpoint-level `model`/`effort` — only the global `runtime.*` fields appear. A user asking "can I run this one cron job on a stronger model?" gets a false "not configurable" answer.

4. **[P2] [verifier: CONFIRMED]** — `references/package-map.md` never mentions `@mono-agent/session-web`, the package that actually implements `mono-agent web`. `mono-agent web` is referenced repeatedly elsewhere in the same skill, but package-map's Observability Join table attributes web only to `operator-adapter`; ownership is proven via `web-command.ts:5` (`import { startSessionWebServer } from "@mono-agent/session-web"`). Compounding gap: `feature-coverage.md:83`'s web-PWA row lists only `[--host] [--port] [--no-open] [--allow-non-loopback] [--include-memory]` and omits `--show-auth-url`, `--max-runs`, and the `MONO_AGENT_WEB_AUTH_TOKEN` requirement documented at `feature-registry.md:158` — a security-relevant gap for non-loopback exposure guidance.

5. **[P2] [verifier: CONFIRMED, with nuance]** — Supermemory backend (`memory.backend`, `@mono-agent/memory-supermemory`) undocumented in `feature-coverage.md` and `package-map.md` despite being demonstrated in the skill's own playbook 13 ("Personal Telegram assistant with Supermemory"). Real config field (`config/src/types.ts:254`, enum `enums.ts:22` `MEMORY_BACKENDS = ["bujo","supermemory"]`). **Verifier nuance:** `SKILL.md:62` deliberately delegates Supermemory to "their own setup skill," so partial omission is by-design — but that does not excuse shipping playbook 13 while the two "exhaustive" tables never name `memory.backend` at all. Finding holds at P2.

6. **[P3] [verifier: CONFIRMED, severity settled]** — `config-blueprint.md:38`'s `runtime.effort` comment documents only 6 of the real 8 enum values (`none|low|medium|high|xhigh|max`), missing `minimal` and `ultra`. Real enum: `packages/config/src/enums.ts:10` = `["none","minimal","low","medium","high","xhigh","max","ultra"]`. Both missing values are legitimate, documented, settable (`feature-registry.md:135`). Raw audit filed this as P2/P3; verifier settles it at **P3** given it's a single inline comment, not a missing capability.

7. **[P1/P2, non-blocking] [verifier: NEW]** — composer-reference drift is broader than the six enumerated findings; three more shipped, config-reachable capabilities are entirely absent from `references/*`:
   - **`runtime.routeSafety`** (`uniform`/`per-route-native`) — real key (`config.ts:153`, `config-view.ts:71,327`, `enums.ts:13`), documented at `feature-registry.md:33`, zero hits anywhere in composer references.
   - **`concurrency.{maxConcurrentRuns,maxPendingRuns}`** — real key (`config/src/types.ts:228-230`), documented at `feature-registry.md:40`, and **used in the composer's own playbook 2** (`playbooks.md:44`), yet absent from `feature-coverage.md` and `config-blueprint.md`.
   - **`interaction.{bridge,askUser,progress}`** — real app-level config block loaded by `interaction-bridge.ts:88-114`, and **used in the composer's own playbook 15** (`playbooks.md:263`), yet absent from both reference tables.

   These share findings 1/3/5's exact root cause (a feature ships a `feature-registry.md` row but never gets back-ported into the composer references). Cases 2 and 3 are sharper: the skill's *own playbooks* depend on config keys its "exhaustive" tables never name.

## Quarantine (refuted/unproven)

- **G1-1 as freeze-blocker** — REJECTED by verifier. Real shipped feature (native `notify`), invisible in a reference claiming exhaustiveness, but the feature itself works and is documented in `feature-registry.md`; the composer just can't discover it. Documentation-completeness defect, not a secret/license/correctness catastrophe, not runtime-honesty-falsifying. Downgraded to P1 non-blocking.
- **G1-2 as freeze-blocker** — REJECTED by verifier. The taught config still functions (posts via a valid `SlackSendMessage` tool); it is one feature-generation stale versus the doc it claims to mirror. Doc-freshness quality gap, not a hard ship-blocker.
- **G1-3 as freeze-blocker** — REJECTED by verifier. Same class as G1-1: a real, validated, config-only capability absent from the "exhaustive" table — a P1 completeness gap, not a blocker.

Rationale (verifier, held consistent with V6's disposition of the parallel E1-1/2/3): the freeze bar is "blocks a DoD clause / secret-license-correctness catastrophe / makes honest ops false." All three are content-accuracy defects in a bundled skill's reference tables whose underlying framework code is correct and shipping. The worst realistic harm is a composed agent's operator being told a real feature doesn't exist — a genuine quality regression worth clearing in the pre-freeze doc-sweep, but it exposes no secret, corrupts no data, and does not make the running agent misreport what it did.
