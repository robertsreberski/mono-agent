# C5-messaging-adapters — telegram & slack adapters

## 1 Verdict & maturity grade

**Grade: B+.** Both adapters are genuinely mature, carefully-reasoned pieces of engineering — the kind of code a stranger can read top-to-bottom and trust. The flagship reliability mechanisms (Telegram's long-poll auto-restart loop, Slack's Socket-Mode reconnect/heartbeat loop) are root-caused, bounded, and backed by real fake-timer tests that simulate the exact failure modes they claim to handle (10,426 lines of tests across the two packages; `start.test.ts` alone drives a 1,013-line suite that includes a test literally titled "uses the exact 90s retry budget and absorbs an isolated timeout inside one runner"). Telegram's secret-redaction module (`log-redaction.ts`) is unusually thorough for a package this size. Interaction features (ask-buttons, reactions, Slack shortcuts/Home-tab) are well-scoped and defensively coded (bounded dedupe sets, best-effort side-effects that never fail a turn).

What keeps this from an A: one correctness/consistency defect repeats **identically in both adapters** (structural JSON config — Telegram's `sendTools`, Slack's `shortcuts`/`homeTab` — is validated *before* the `enabled` check, unlike every other structural field in the same functions, so a disabled channel with a stale/malformed config block still hard-fails config load); the READMEs quote a public-API symbol (`telegramFieldGroup` / `slackFieldGroup`) that was renamed away and no longer exists, which is exactly the kind of drift that breaks the "lean core a stranger can pick up" promise; and there is a fully dead exported function (`redactSlackAdapterConfig`) alongside a parallel, hand-maintained redaction mechanism that has already drifted out of sync with the app's real (generic, field-spec-driven) config-provenance surface.

**On the focus question ("did PR #243 actually fix the getUpdates timeout→restart loop?"):** yes. Before #243, the grammY runner's internal retry budget for `getUpdates` was 15s (`DEFAULT_RUNNER_MAX_RETRY_TIME_MS`), well under a single HTTP timeout (the Api client is capped at 50s — `DEFAULT_API_TIMEOUT_SECONDS`), so one slow/failed poll could exhaust the budget and crash the runner, triggering a full restart cycle for what was often a transient network blip. #243 (closing goal #239) raised the budget to 90s — deliberately kept under the 120s poll-liveness watchdog (`DEFAULT_POLL_WATCHDOG_MS`) so an isolated timeout is absorbed *inside* the same runner while a genuinely sustained outage still hits a hard, bounded liveness check — and fixed the recovery-detection logic to require an actual successful `getUpdates` resolution from the *same* runner generation (not merely "stayed up past the stability window"), which previously could false-positive a "recovered" callback. Both properties (bounded restart-free absorption of transient errors; single degraded/single recovery edge per outage) are exercised by dedicated tests (`packages/telegram-adapter/src/__tests__/start.test.ts:173`, `:571`, `:775`, `:940`). This is not config tuning or a band-aid — it is a real, tested, root-caused fix; nothing about the loop is now "inherent" in the sense of being unfixable, and it isn't merely papered over.

## 2 Findings

**F1 — [P1] Disabled-channel structural config is still hard-validated, contradicting the adapters' own documented invariant, in *both* adapters.**
`packages/telegram-adapter/src/config.ts:185` — `const sendTools = readTelegramSendTools(json);` runs **before** the `if (!enabled) { return … }` early-out at line 190, so a malformed `telegram.sendTools` block (e.g. an unknown field, or `scope` set to something other than `"producing-conversation"`) throws a hard `TelegramAdapterConfigError` even when `telegram.enabled` is `false`. This directly contradicts the comment two lines above the early-out: *"A disabled channel never validates its credentials: the status surface reads it as 'disabled', not 'waiting for config'."* Every other structural JSON field in the same function (`quietHours`, `commands`, `reactions`, `apiRoot`, `attachments`, `transcription`) is read only *after* the enabled check (lines 222–227), so `sendTools` is the one field that breaks the pattern.
The identical bug shape exists in Slack: `packages/slack-adapter/src/config.ts:149-150` — `const shortcuts = readSlackShortcuts(json); const homeTab = readSlackHomeTab(json);` both run before the `enabled` read (line 151) and the `if (!enabled) return {...}` early-out (line 171). A malformed `slack.shortcuts` or `slack.homeTab` block will hard-fail config load even with `slack.enabled: false`.
**Why it matters:** the premise promises "agents in seconds-to-minutes" and "honest ops." A user who disables a channel to sidestep a config problem (a completely natural workflow step) can instead find their whole config load / `mono-agent validate` / `doctor` still fails, with no indication that the failing block belongs to a channel they just turned off. `config.test.ts` for both packages only exercises "disabled + empty config" (`telegram: config.test.ts:113-121`, `slack: config.test.ts:185-199`), never "disabled + malformed structural block," so this gap is untested as well as unfixed.

**F2 — [P2] READMEs advertise a public-API symbol that no longer exists.**
`packages/telegram-adapter/README.md:44,55` and `packages/slack-adapter/README.md:36` show `telegramFieldGroup` / `slackFieldGroup` as importable/public API. Neither symbol is exported by the current `index.ts` (`packages/telegram-adapter/src/index.ts:103-121`, `packages/slack-adapter/src/index.ts:99-114`) — both were renamed to `TELEGRAM_CONFIG_FIELDS` / `SLACK_CONFIG_FIELDS` during the config-consolidation work and are the names actually consumed downstream (`packages/agent-app/src/config-reference.ts:22-23,42-43`, `packages/agent-app/src/channels.ts:229,370`). Copy-pasting the README's own usage example (`packages/telegram-adapter/README.md:39-46`) would fail at import time.
**Why it matters:** the premise explicitly wants "a lean, understandable core open to external plugins" — the README is the first thing an external integrator reads, and it is factually wrong about the package's own public surface.

**F3 — [P2] `showThoughts` is a fully dead, no-op configuration field threaded through the entire Telegram stack.**
Declared and forwarded at `packages/telegram-adapter/src/adapter.ts:190` (`TelegramAdapterStreamOptions.showThoughts`), `packages/telegram-adapter/src/bot.ts:1255-1256` (`if (tuning?.showThoughts !== undefined) { streamOptions.showThoughts = tuning.showThoughts; }`), and `packages/telegram-adapter/src/message-stream.ts:49` (`TelegramMessageStreamOptions.showThoughts?: boolean`) — but the `TelegramMessageStream` constructor (`message-stream.ts:252-307`) never reads `options.showThoughts` when building the inner `ResilientMessageStream` options; it is silently dropped. `packages/agent-app/src/channels.ts:1440` unconditionally sets `showThoughts: true` in the live stream config for every Telegram agent, believing it does something. Slack's equivalent `SlackAdapterStreamOptions` (`slack-adapter/src/adapter.ts:147-160`) has no such field at all — it was correctly dropped there.
**Why it matters:** a config knob that is documented ("Retained for compatibility... this is a no-op") but still fully wired end-to-end (including a hard-coded call site believing it's live) is exactly the kind of leaky abstraction that erodes "a lean, understandable core."

**F4 — [P3] `redactSlackAdapterConfig` is dead exported code; its Telegram sibling is a second, hand-maintained redaction path that has already drifted from the app's real config-provenance mechanism.**
`packages/slack-adapter/src/config.ts:432-449` defines and `index.ts:99-104` exports `redactSlackAdapterConfig`; a repo-wide search finds **zero** production or demo consumers (only its own definition/export and, presumably, its unit test). Its Telegram counterpart `redactTelegramAdapterConfig` (`telegram-adapter/src/config.ts:605-624`) has exactly one consumer in the whole repo: `demos/final-agent/src/configuration.ts:19,58`. The actual production host (`agent-app`) redacts channel config through a completely different, generic mechanism (`buildChannelConfigView` + `TELEGRAM_CONFIG_FIELDS`/`SLACK_CONFIG_FIELDS`, `packages/agent-app/src/channels.ts:229,370`, `config-reference.ts:22-43`) that carries its own `secret: true` markers per field. Two independently-maintained redaction paths for the same config shape is a duplication risk: a newly-added secret field could be added to `TELEGRAM_CONFIG_FIELDS`/`SLACK_CONFIG_FIELDS` (used by the real app) without a matching update to the adapter's own hand-rolled `redact*AdapterConfig` (used only by a demo, or by nothing).

**F5 — [P3] Slack has no quiet-hours / silent-delivery parity with Telegram.**
Telegram's config surface (`telegram-adapter/src/config.ts:28-32,504-565`) defines `TelegramQuietHours` and `isWithinQuietHours`, and its `TelegramNotifyOptions`/stream plumbing (`bot.ts:145-152`, `message-stream.ts:63-66`) carries a `silent` flag end-to-end. Slack's `SlackNotifyOptions` (`slack-adapter/src/adapter.ts:121-125`) has only `verbatim` and `deliveryKey` — there is no `silent` concept anywhere in `slack-adapter/src` (confirmed by grep: the only "silent" hits in the package are about a silently-dead heartbeat socket, unrelated). A cron/webhook quiet-hours policy therefore cannot be honored uniformly across channels from inside these packages.
**Why it matters:** "channels easily" implies parity — an operator configuring a proactive-notification policy should not need to know that it silently does nothing on one of the two flagship channels.

**F6 — [P3] Slack's error-text is a plain string; Telegram's supports a computed callback.**
`TelegramAdapterErrorText` (`telegram-adapter/src/adapter.ts:174-181`) is `string | ((input) => string | Promise<string>)`, resolved via `resolveErrorText` (`adapter.ts:908-934`) with a documented empty-result/callback-throw fallback. `SlackAdapterMessages.errorText` (`slack-adapter/src/adapter.ts:143`) is `string` only, and `respondToEvent` (`adapter.ts:1408-1412`) uses it verbatim with no equivalent extension point. Minor, but another asymmetry between the two "flagship" channels.

**F7 — [P3] Slack has no analog of Telegram's secret-redaction module.**
Telegram ships a 348-line dedicated module (`telegram-adapter/src/log-redaction.ts`) that deep-sanitizes arbitrary log values/errors (token patterns, bearer/auth headers, query-string secrets, nested `cause` chains, circular-reference guards) before anything reaches a logger. Slack has nothing comparable: `slack-client.ts` and `adapter.ts` log with plain `error instanceof Error ? error.message : String(error)` (e.g. `slack-adapter/src/adapter.ts:1252-1255,1280-1283`) and construct `SlackApiError` without ever embedding the bot/app token in `message` today, so there is no active leak — but there is also no defense-in-depth if a future change starts logging a raw response/fetch error object that happens to carry request headers.

## 6 Skill-worthy flags

- **Repeated correctness bug across sibling packages (F1):** the exact same "structural JSON parsed before the `enabled` early-out" mistake exists in both `telegram-adapter/config.ts` and `slack-adapter/config.ts`. This is the shape of bug a **code-review** pass at "high" effort on config-loader functions should catch by pattern-matching: *"for every field parsed in a `loadXConfig` function, is it parsed strictly after the same function's own `if (!enabled) return` guard, or is there a documented reason it's exempt?"* Worth adding as an explicit checklist line to the `code-review` skill (or a `new-package`/`verify-green` amendment) for any package with an opt-in `enabled` flag: grep the loader for every `read*(json)` call site and confirm none precede the enabled check without a comment explaining why.
- **README/public-API drift after a rename (F2):** `telegramFieldGroup`/`slackFieldGroup` → `TELEGRAM_CONFIG_FIELDS`/`SLACK_CONFIG_FIELDS` was renamed in the config-consolidation work but the two READMEs' own code samples were never updated. The `docs-sync` skill's per-PR workflow should add a concrete step: *"when a PR renames or removes an exported symbol, `grep -rn '<old-name>' packages/*/README.md docs/` before closing out the PR's doc-sync pass"* — this is a cheap, mechanical check that would have caught F2 immediately.
