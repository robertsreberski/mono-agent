# F2-live-a8c-fleet — Live instance: a8c-agents fleet (orchestrator → broker → 4 specialists → Brain)

## 1 Verdict & maturity grade

**Instance maturity grade: B+.** This is the single most sophisticated real deployment of mono-agent observed in this audit: 9 coordinated launchd services (5 model workers + Brain Core + control broker + attention collector + proactive scheduler), ~4 bespoke TypeScript packages (`brain-core`, `control-broker`, `attention-collector`, `gws-a8c`), a 3763-line lifecycle manager (`bin/agents`), and a 7754-line/~266-case test suite (`test/fleet/*.test.js`). Docs (`README.md`, `docs/architecture.md`, `docs/runbook.md`, `docs/migration.md`) are exhaustive, internally consistent, and match what the code and live logs actually do — a rare and valuable property. The instance shows real, moderate production usage two days post-migration (75 delegation tasks, 110 acknowledged results). It also survived and correctly reported a real operational incident (a 108-iteration crash loop, see F1) rather than silently masking it. Deductions: zero automated crash-loop protection anywhere in the 9-service launchd fleet (F1), ~1.5 GB of unreviewed dead weight from three retired agents with no soak-period end date (F7), and one long-overdue delivery item that nothing pages a human about (F9).

**Framework-fit grade: C+.** The low-level primitives the framework advertises — config-first agent folders, `cron/*.md` authoring, native `notify`, the sandbox, the A2A adapter as a transport, Slack's native adapter — are all used cleanly and exactly as designed (see the three `orchestrator/cron/*.md` briefings, which are simple, idiomatic, and effective). But the *moment* this instance needed multi-agent reliability guarantees or a shared knowledge base — the two things the v1 premise explicitly promises ("crons, webhooks, and channels easily," "clean memory") — it had to build almost everything itself: the framework's own Memory v2/BuJo subsystem is disabled or absent across all five agents in favor of a hand-rolled knowledge base (F2); the A2A adapter provides transport only, so at-most-once execution, durable outbox, dead-lettering, and reconciliation were all built in userland (F3); and there is no framework-level fleet/launchd tooling at all, so credential rotation, migration/rollback, and process supervision are a bespoke 3763-line script (F4). None of this is a bug in the framework — it is evidence about where the "lean core" premise stops paying off for a demanding, safety-conscious real deployment.

## 2 Findings

**F1 [P1] — Zero automated crash-loop circuit breaker; a bad credential crash-looped Brain Core 108 times before a human intervened.**
`~/Library/Logs/a8c-agents/brain-core.log` lines 45–152 contain 108 consecutive identical lines:
```
a8c-brain serve failed: A8C_BRAIN_ATTENTION_TOKEN must contain at least 32 characters.
```
Every one of the 9 launchd plists this fleet generates uses the same policy, e.g. `bin/agents:966-969` (`write_agent_plist`) and `bin/agents:1479-1481` (`write_brain_plist`):
```
<key>KeepAlive</key><true/>
<key>ThrottleInterval</key><integer>10</integer>
```
`KeepAlive=true` + a flat 10-second `ThrottleInterval` with no consecutive-failure counter means a bad or partially-rotated credential file restarts the process indefinitely at a fixed cadence (108 restarts × 10 s ≈ 18 minutes minimum, evidenced here; unbounded in general) rather than failing once, loudly, and staying down. `bin/agents`'s only readiness/backoff loop, `agent_start` (`bin/agents:1021-1027`, 60 × 0.5 s), guards only the operator-invoked `./bin/agents start` path — it never runs when launchd auto-restarts an already-loaded service, so this guard cannot see or stop the loop. Evidence ties the incident to 2026-07-13 ~10:38–15:09 (correlates with `backups/brain/brain-20260713T103843Z.sqlite.invalid-20260713T125902Z-39832`, a backup that was *correctly* rejected by the integrity verifier during the same window). Violates the premise's "honest ops": nothing pages an operator during a crash loop; discovery depends entirely on someone reading the log or running `doctor`.

**F2 [P2] — The framework's own Memory v2 (BuJo/recall) subsystem is unused fleet-wide; a fully custom knowledge base replaces it.**
`attention-radar/mono-agent.config.json:47-55` (byte-identical pattern in `delivery-copilot` and `knowledge-steward`):
```json
"memory": {
  "mode": "lite",
  "writeMode": "disabled",
  "recallTool": { "enabled": false }
}
```
`orchestrator/mono-agent.config.json` and `deep-research/mono-agent.config.json` omit the `memory` key entirely. Every agent instead reaches durable knowledge exclusively through `@a8c-agents/brain-core` (`packages/brain-core`) — a hand-built SQLite+FTS5+embeddings service with temporal validity, supersession, retraction, sensitivity floors, and a leased approval queue (`docs/architecture.md:163-193`). For the fleet that most needs "clean memory" (5 agents sharing curated context with role-scoped access and an approval workflow), the framework's shipped memory feature was not merely insufficient — it was not used at all.

**F3 [P2] — The A2A adapter supplies transport only; all delivery-reliability semantics were hand-built in userland.**
`scripts/agent-host.mjs:771-1191` implements a complete logical-task claim/receipt ledger (`createPermanentTaskClaim`, `runWithDurableTaskReceipt`, `logicalTaskReceiptOutcome`) whose entire purpose is to give `@mono-agent/a2a-adapter` requests at-most-once execution semantics the adapter does not itself provide across retried transport calls. On top of that, `packages/control-broker` (dozens of source files: `outbox.ts`, `reconciliation.ts`, `continuations.ts`, `delegations.ts`, `leases.ts`, `migration.ts`, `checkpoints.ts`, `state-guard.ts`, `terminal-fallback.ts`) reimplements durable delegation, an outbox with exponential backoff and dead-lettering, reconciliation, and an offline v1→v2 schema migration — none of which any `@mono-agent/*` package provides.

**F4 [P2] — No framework-level fleet lifecycle tooling exists; the instance reimplements process supervision, credential rotation, and migration/rollback entirely in bash.**
`bin/agents` is 3763 lines implementing a kernel-`flock`-backed lock (`acquire_manager_kernel_lock`, `bin/agents:253`), owner-only residual-process-identity tracking across restarts (`record_residual_process`, `bin/agents:398`), a single-use nonce-authorized credential-rotation protocol (`fleet_rotate_credentials`, `bin/agents:1430`), and a full offline snapshot/verify/restore migration system (`scripts/v2-migration-snapshot.mjs`, 96 KB; `docs/migration.md`). This is high-quality engineering, but it is infrastructure the mono-agent framework does not offer any consumer, forcing every serious multi-agent deployment to build its own equivalent from scratch.

**F5 [P3] — No framework concept of a shared/canonical skill across agent instances; the fleet must copy files and validate byte-equality by hand.**
`skills-shared/{agent-result,brain-context,context-a8c,report-back}/SKILL.md` are the source of truth, physically duplicated into each of the 5 agents' own `skills/` directories (confirmed via directory listing, not symlinks — e.g. `attention-radar/skills/agent-result/`, `delivery-copilot/skills/agent-result/`, ... are five separate copies). `scripts/validate-fleet.mjs:247-266` re-reads `skills-shared/*` and diffs it against every per-agent copy specifically to catch drift, because `context.skillsRoot` is per-instance-only in the framework's config schema.

**F6 [P3] — The exact expected `@mono-agent` version is hardcoded independently in 6 files with no single source of truth.**
`scripts/agent-host.mjs:22` (`const EXPECTED_MONO_AGENT_VERSION = "0.11.2"`), `scripts/mono-agent-lock-policy.mjs:4`, `scripts/verify-live-fleet.mjs:13`, `scripts/validate-fleet.mjs` (6+ occurrences, e.g. line 190), and `bin/agents` (e.g. lines 915-929, 3260-3290) each carry their own copy of the literal string `"0.11.2"`. Historical logs show this fleet has already tracked 0.8.0 → 0.9.0 → 0.9.1 → 0.10.0 → 0.11.0 → 0.11.1 → 0.11.2 (six releases), each requiring a consistent manual edit across all six files. All checks fail closed on mismatch (safe), but this is recurring toil with no single derivation point.

**F7 [P2] — ~1.5 GB of dead weight from 3 fully retired agents, still refreshed in lockstep with current mono-agent versions, no soak-period end date.**
`activity-digest/` (487 MB), `p2-watcher/` (501 MB), `slack-sweep/` (541 MB) each retain their own `node_modules`, `pnpm-lock.yaml`, and `pnpm-workspace.yaml`, even though the root `pnpm-workspace.yaml` (`/Users/example/a8c-agents/pnpm-workspace.yaml:1-7`) no longer lists any of them. Each directory's `package.json`/`pnpm-lock.yaml` carries the same mtime (2026-07-15 16:48) as the active root workspace's own refresh, and each still pins `@mono-agent/agent-app` to the current `0.11.2` — meaning something is still keeping these dead trees version-current. `docs/migration.md:11` only says "Do not delete them until the new fleet has passed an agreed soak period," with no date, owner, or tracking ticket recorded anywhere in scope.

**F8 [P3] — `legacy/` is a fully empty directory with no explanation.**
`ls -la ~/a8c-agents/legacy` returns only `.` and `..`. It is referenced nowhere in `README.md`, `docs/architecture.md`, `docs/runbook.md`, or `docs/migration.md` beyond the general "retired ... directories" language, which actually refers to `activity-digest/`, `p2-watcher/`, and `slack-sweep/` (still in place at the top level, not inside `legacy/`). The directory's purpose is undocumented and it currently does nothing.

**F9 [P2] — Live evidence: an overdue retryable delivery sits unresolved for hours with no push alert; discovery is manual-only.**
`data/control-broker/result-outbox/pending/3fa4c69...json` (mtime 2026-07-15 15:08) contains `"lastError":{"code":"destination_channel_unavailable","retryable":true}` with `nextAttemptAt: 2026-07-15T13:54:25.752Z`. At inspection time (2026-07-15 21:39 CEST / 19:39 UTC) this is roughly six hours past its own retry window. `docs/runbook.md:124` states plainly that "every unresolved result at least five minutes old is overdue" and that `control status`/`doctor` degrade — and indeed `control-broker.log` shows the broker correctly flagging `"degraded":true` on the relevant replay cycles — but nothing pushes that state to Robert; discovery requires manually running `./bin/agents control health`.

**F10 [P3] — Specialist launchd logs carry zero visible task/turn activity; real usage evidence exists only in an internal file ledger.**
`attention-radar.log`, `delivery-copilot.log`, `deep-research.log`, and `knowledge-steward.log` are each exactly 27 lines long, and every line is a `{"status":"running",...}` host-restart/version-bump entry — none show any per-task or per-turn activity. The only proof the specialists are doing real work is the broker's file-based ledger (`data/control-broker/delegation-ledger/tasks/`: 75 files; `data/control-broker/result-outbox/acked/`: 110 files), which `./bin/agents logs <worker>` does not surface. An operator using only the documented `logs` command cannot see whether a specialist is idle or busy.

## 6 Skill-worthy flags

- **fleet-deploy / live-smoke amendment — post-restart crash-loop check.** After restarting or deploying any launchd-managed service, the skill should tail the service's log for N (e.g. 5) identical failure lines within a short window and fail the deploy rather than declaring success once the process is merely "loaded." This exact gap let brain-core crash 108 times on 2026-07-13 before detection. Seed command: `tail -n 20 <service log> | sort | uniq -c | sort -rn | head -1` — if the top count exceeds a small threshold and the message looks like an error, treat the deploy as failed.
- **Credential rotation/init — validate-after-write, not validate-at-next-start.** `ensure_specialist_brain_tokens` (`bin/agents:1151`) and `init-a2a-env.mjs` both generate tokens correctly (`randomBytes(32)`/`openssl rand -hex 32`, i.e. 64 hex chars), yet a sub-32-character token still reached `.brain.env` and crash-looped the service. The generation code was fine; the credential file was apparently edited/rotated outside the generator once. Any skill covering credential rotation (fleet-deploy, or a dedicated credential-rotation skill) should add: immediately after writing any owner-only env file, re-read it back and re-run the exact validation the consuming service performs, failing the rotation command itself rather than deferring discovery to the next process start.
- **release-lockstep amendment — single version-derivation point for downstream consumers.** This instance hardcodes the exact `@mono-agent` release string in 6 separate files (F6). When documenting how downstream fleets should track lockstep releases, recommend deriving the expected version at runtime from the consumer's own `package.json` rather than literal-string duplication, to reduce upgrade toil that recurs on every release.
