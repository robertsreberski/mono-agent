# E1-docs-website — docs & website

## 1 Verdict & maturity grade

**Grade: B+**. This is an unusually thorough documentation suite for a v1: 76 markdown files under `docs/`, a genuinely comprehensive `feature-registry.md` (204 lines) that tracks nearly every shipped capability including the newest 0.11.x features (durable continuations, A2A idempotency, forget plans, the capability-module wizard), 15 end-to-end playbooks that all follow the same init→configure→validate→start→smoke arc, and a well-engineered website build (Astro Starlight, isolated pnpm workspace, a real link-integrity gate that fails closed on an empty mirror). The prose is exhaustive to the point of being occasionally hard to parse (see §2), but it is accurate almost everywhere I could verify it against source.

The grade is B+ rather than A because I found two shipped, validated, real config surfaces (`slack.homeTab`, `slack.shortcuts`, and separately `telegram.transcription`) that are essentially invisible to a reader — present only as bare rows in an auto-generated table, never in the prose page a user would actually read to configure that channel — plus one direct self-contradiction in the glossary about core memory behavior (salience decay), plus a systemic content-rendering bug (16 empty callout boxes with their content silently orphaned outside the box) that no CI check catches. None of these are functional/security defects; they are exactly the class of finding this audit exists to surface — docs promising or omitting behavior the code does or doesn't have.

## 2 Findings

**F1 (P1) — Glossary directly contradicts the rest of the docs on memory consolidation and salience behavior.**
`docs/reference/glossary.md:98-100`:
> "A scheduled BuJo maintenance pass run by the in-app scheduler (no external cron needed): salience decay, near-duplicate superseding, `index.md` refresh, and an empty retired `future-log.md` stub."

`docs/reference/glossary.md:110-112` ("Salience" entry):
> "The decay-weighted importance score the journal and BuJo tiers attach to memories, so older, less-reinforced items rank lower in recall."

Both entries describe decay/superseding behavior that four *other* doc pages explicitly say does **not** happen. `docs/memory/rituals.md:15-18`:
> "Consolidation is a lightweight, projection-only housekeeping cycle... In v1, salience is static canonical Markdown metadata: scheduled consolidation does not decay it, and it never supersedes, deletes, or rewrites canonical memories."

Same claim repeated in `docs/memory/index.md:44` and `:239` ("It never decays salience or automatically supersedes..."), `docs/memory/backends-comparison.md:95`, and `docs/reference/feature-registry.md:81` ("It never decays salience or automatically supersedes/rewrites canonical memory"). The glossary — which exists specifically to give a competent stranger a correct one-paragraph definition of each term — is the one page still describing an earlier design (decay + superseding) that was simplified away before v1 and never updated. Premise clause: "clean memory (+ a way to preview it)" and "legible sessions" both depend on operators trusting what the docs say memory actually does; this glossary entry will actively mislead an operator into believing scheduled consolidation mutates canonical facts over time.

**F2 (P1) — `telegram.transcription` (a real, shipped, opt-in feature) is undocumented on the page a user would actually read.**
`packages/telegram-adapter/src/config.ts:280-283` reads four real env vars (`MONO_AGENT_TELEGRAM_TRANSCRIPTION_ENDPOINT/_MODEL/_LANGUAGE/_TIMEOUT_MS`) and the feature is fully described in `docs/reference/feature-registry.md:123`. But:
- `docs/channels/telegram.md` — the per-channel setup guide — never mentions transcription anywhere (verified: zero matches for "transcription" in the file).
- `docs/config/env-vars.md` — which states at the top "This page is the exhaustive reference" of every `MONO_AGENT_*` var — has zero matches for `TRANSCRIPTION` anywhere in the file, despite listing every other Telegram env var (`_REACTIONS`, `_IP_FAMILY`, `_POLL_WATCHDOG_MS`, `_API_ROOT`, `_ATTACHMENT_*`) individually.
- The one automated check that exists for this exact promise, `packages/agent-app/src/__tests__/env-vars-docs-parity.test.ts`, only asserts full env-key coverage for the `MONO_AGENT_OPENAI_API_*` prefix (`it("documents every OpenAI API env key...")`, lines 110-115) — it does not check Telegram, Slack, or any other adapter, so this exact gap is untested and silent.

A user setting up Telegram from `docs/channels/telegram.md` (the natural, and only linked, starting point) has no way to discover this feature exists.

**F3 (P1) — `slack.homeTab` and `slack.shortcuts` are fully implemented, validated config surfaces with zero prose documentation anywhere.**
`packages/slack-adapter/src/config.ts:19-45` defines and validates `SlackShortcutConfig` (global/message shortcuts that run a prompt, with `channelId`/`ackText`/`threadReply`) and `SlackHomeTabConfig` (App Home tab with clickable buttons that each run a prompt). Both are real, wired, tested features. Yet:
- `docs/channels/slack.md` never mentions either.
- `docs/reference/feature-registry.md` and `docs/reference/feature-matrix.md` have no rows for them.
- `packages/slack-adapter/README.md` has zero matches for either name.
- The **only** place either field appears in the entire docs tree is `docs/config/reference.md:275-290` — the auto-generated field table — with hand-authored but deliberately terse placeholder text ("Slack shortcut definitions handled by the Slack adapter.", "Slack app home tab configuration.") sourced verbatim from `packages/agent-app/src/config-reference.ts:275-290`.

This is a direct violation of `feature-registry.md`'s own "Maintenance rules" (`docs/reference/feature-registry.md:189-191`): "A new option in any package is **not done** until it has a row here... When a feature row changes, also update its prose page under `docs/<area>/`." Someone added the config-reference entry (satisfying capability-ladder rung 2's "typed config, validation") but never the registry row or the prose section that rule requires.

**F4 (P2) — Systemic broken-aside bug: 16 empty Starlight callouts across 13 files, with the intended content silently orphaned outside the box.**
A precise scan (opening aside fence immediately followed by closing fence, no body) found 16 instances:
`docs/config/blueprint.md:367`, `docs/runtime/local-providers.md:133`, `docs/runtime/index.md:100`, `docs/runtime/tools-and-guards.md:39,92`, `docs/programmatic/multi-agent.md:22,100`, `docs/programmatic/a2a-consumer.md:51,234`, `docs/observability/artifacts-and-traces.md:188`, `docs/getting-started/concepts.md:99`, `docs/channels/openai-api.md:106`, `docs/channels/a2a.md:35,165`, `docs/channels/telegram.md:39,150`. Example (`docs/channels/telegram.md:39-42`):
```
:::caution
:::
`allowAllChats: true` lets anyone who finds your bot send it messages...
```
The caution text clearly belongs *inside* the box (it reads exactly like every other properly-formed `:::caution` block in the same file) but renders as plain paragraph text below an empty, content-free callout. This almost certainly originated in the one-off Jekyll→Starlight migration (`website/scripts/migrate-callouts.mjs`, kept "for reference" per `website/README.md:41-43`, not re-run) mishandling a marker variant. Nothing in the build pipeline catches it: `website/scripts/check-links.mjs` validates only `href`/`src` resolution against the built `dist/`, not aside/content rendering. This is exactly the kind of "docs site cannot rot silently" gap the website CI job's own comment (`.github/workflows/ci.yml:103-106`) says it exists to prevent — link rot is prevented, content rot is not.

**F5 (P2) — Playbook code sample contradicts the documented API of the function it demonstrates.**
`docs/playbooks/multi-agent-orchestration.md:33-46` shows:
```ts
const extension = createCollaboratorToolRuntimeExtension({
  collaborators: [...],
  conversationId: input.conversationId,
  maxCalls: 10,
});
return { runtimeOptions: extension.runtimeOptions, cleanup: extension.cleanup };
```
But `docs/programmatic/multi-agent.md` — the reference page for the same function — documents `originalUserMessage` and `abortSignal` as `(required)` options (its own table, rows 2-3) and shows the call `await`-ed (`docs/programmatic/multi-agent.md:88-96`), because the extension starts an ephemeral HTTP MCP server. The playbook sample also reads `input.conversationId` directly, but the documented `runtimeOptionsForRequest` callback signature is `{ request, runId, context }` (`docs/programmatic/composition.md:159-168`), so the correct access path is `input.request.conversationId`. A reader who copies the playbook's snippet verbatim gets code missing two required fields, a missing `await`, and an undefined property read.

**F6 (P2) — The docs-site CI gate is not actually enforced; it relies on convention.**
`website/README.md:27`: "This repo does not use GitHub required-status-check enforcement, so nothing blocks a merge automatically — a red **website** check must be treated as a merge blocker by convention (do not merge over it)." Combined with F4 (a real, already-shipped content defect the gate's checker cannot detect even in principle), the "honest ops" premise clause is only partially met for this surface: the mechanism that is supposed to keep docs from rotting is (a) narrower in scope than advertised (links only, not content) and (b) not a hard gate even for what it does check.

## 3 Dead code

- **`website/scripts/migrate-callouts.mjs`, `migrate-frontmatter.mjs`, `migrate-links.mjs`** — one-off Jekyll/just-the-docs → Starlight conversion scripts. Why dead: explicitly self-described as one-off in their own header comments and in `website/README.md:41-43` ("kept for reference; you do not run them in the normal authoring loop"); not referenced by any `package.json` script or CI step (verified via grep across `website/package.json` and `.github/workflows/ci.yml`). Proposed disposition: low-priority — either delete (git history preserves them if ever needed again) or move to a clearly-labeled `website/scripts/archive/` so they stop appearing as live tooling next to `sync-content.mjs`/`check-links.mjs`, which *are* exercised on every build. Not urgent; explicitly and honestly disclosed already, so this is a tidiness call rather than a correctness risk. Proof hint: `grep -rn "migrate-callouts\|migrate-frontmatter\|migrate-links" website/package.json .github/workflows/ci.yml` returns nothing.

No other dead code found in the docs/website scope — the rest of `website/scripts/` (`sync-content.mjs`, `check-links.mjs`) is live and exercised by CI on every push (`.github/workflows/ci.yml:126`).

## 4 Deprecation & legacy

Every deprecated/legacy surface actually referenced in `docs/**` is a documented, load-bearing back-compat shim with a clear migration path — this is a model example of how to do it, not a finding:

- **`mono-agent recipes` → alias of `presets`** and **`mono-agent init --recipe <id>` / `validate --recipe <id>`** — `docs/reference/recipes.md:114-123` documents the exact forward-mapping table (`minimal-webhook`→`starter`, etc.) plus which blueprints are fully retired with no replacement (`full-safe`, `full-local-power`, `openai-api-gateway`, `cron-digest`, `a2a-provider`, `phoenix-observed`). Load-bearing: yes (existing automation may still call `--recipe`). Removable-now: no.
- **Legacy snake_case tool names** (`slack_send_message`, `telegram_ask`, `read_skill`, `run_history`, `telegram_send_document`/`telegram_send_photo`) — `docs/tools/policy.md:144-146` and `docs/reference/recipes.md:108-112` both document these as deprecated input aliases still accepted in `allowedTools`/`disallowedTools`, including the non-obvious collapse of two legacy Telegram file tools into one `TelegramSendFile`. Load-bearing: yes. Removable-now: no.
- **`runtime.fallbackModels` / `MONO_AGENT_FALLBACK_MODELS` / `--fallback-models`** — legacy fallback form, documented in `docs/runtime/fallback.md:61-66` and `docs/config/env-vars.md:38-39` as still supported but effort-inheriting (vs. the canonical `runtime.fallbacks[]` per-route effort). Load-bearing: yes. Removable-now: no.
- **`memory.reflection.*` / `memory.migration.*` config keys and their env vars** — `docs/memory/rituals.md:104-106` and `docs/config/env-vars.md:131-136` both state these are "tolerated so stale environments do not break startup, but they are ignored and `mono-agent validate` reports a warning." Correctly classified as retired-but-tolerated, not silently dropped. Removable-now: no (breaking startup for stale environments would be worse than a warning).
- **`@mono-agent/memory-mcp` package** — fully retired from the repo; `docs/memory/capture-and-recall.md:394-397` and `docs/memory/index.md` (References section) both give explicit three-path migration guidance (recall-tool auto-provision, direct library composition, no replacement for the write tools). Removable-now: n/a, already removed; docs are accurate about its status.
- **`@mono-agent/operator-console`** — retired per repo history (PR #28); confirmed **zero** references anywhere in `docs/**`, so there is no stale doc pointing at it. Not a finding.

## 6 Skill-worthy flags

- **docs-sync**: The single biggest recurring pattern this audit surfaced is "a config field gets a `config-reference.ts` entry (so `mono-agent config`/JSON-schema/generated-table stay accurate) but never gets a `feature-registry.md` row or a prose-page section" — exactly the two-step process the registry's own "Maintenance rules" section describes, where step 2 is silently skipped. Seed the `docs-sync` skill with: (1) a checklist item "if you touched `packages/agent-app/src/config-reference.ts`, grep the new `jsonPath` against `docs/reference/feature-registry.md` and the matching `docs/<area>/*.md` prose page before treating the PR as doc-complete"; (2) the exact command that would have caught F2/F3: `comm -23 <(grep -oE '"[a-z]+\.[a-zA-Z]+"' packages/agent-app/src/config-reference.ts | sort -u) <(grep -oE '`[a-z]+\.[a-zA-Z]+`' docs/reference/feature-registry.md | tr -d '`' | sort -u)`.
- **docs-sync** (second amendment): add an automated check for orphaned Starlight asides (E1-6 above) to the `website` CI job's remit, since `check-links.mjs`'s own doc comment claims a broader anti-rot mandate than it actually delivers — the skill should note this is a known blind spot in the current link-checker design, not assume it.
- **release-lockstep** or **docs-sync**: when a playbook demonstrates a `code`-coverage API (no config/CLI to validate it), there is no automated proof the sample still compiles against the current signature — F5 slipped through because playbooks aren't type-checked against the packages they demonstrate. Consider a lightweight `tsc --noEmit` pass over fenced `ts` code blocks in `docs/playbooks/**` and `docs/programmatic/**` as a follow-up (out of scope for a quick fix, but worth a backlog note).
