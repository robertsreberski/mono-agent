# B3-memory-store-search — memory store & search

## 1 Verdict & maturity grade

**Grade: B**

The SQLite store (`store/db.ts` + `schema.ts` + `ranking.ts` + `fts.ts` + `vec.ts`) is genuinely well engineered: hybrid FTS+vector recall is thoroughly tested (stale-candidate exclusion, doubling KNN over-fetch, access-count independence from ranking), the compare-and-swap replay/canonical-graph replacement functions are defensively validated line-by-line, and the deprecated `applyDecay` no-op is honestly documented and spy-tested to confirm nothing calls it. No fake-success paths, no swallowed errors, and no secrets were found anywhere in scope. The `search/` embedding providers (Ollama/LM Studio/OpenAI) and the circuit breaker are correct and well tested (single half-open trial, synchronous JS reentrancy correctly reasoned about).

Two things keep this from an A. First, a real latent gap in exactly the area the audit was asked to check: schema evolution safety. `schema.ts` only ever runs `CREATE TABLE IF NOT EXISTS` — a fine idiom for *adding new tables* (which is the only kind of schema change this package has ever shipped, per git history) but silently inert for adding a *column* to an existing table, and there is no `ALTER TABLE`, no `PRAGMA user_version` check, and no test that opens a stale on-disk schema and asserts migration. The very first time a future column is added the natural way (editing the inline `CREATE TABLE` string), every write against a pre-existing user database will start throwing `SQLITE_ERROR: no column named X` with no automated recovery — even the package's own documented recovery path (`memory rebuild`) only deletes *rows*, not DDL, so it would not fix it either. Second, `packages/memory/src/search/vector-index.ts` + `chunks.ts` (~325 LOC) implement a complete, dependency-free brute-force JSONL vector index and journal/entity chunk-gatherer from the pre-BuJo v1 memory system. It is fully superseded by the SQLite+sqlite-vec `MemoryDb`, has zero consumers anywhere in the monorepo outside its own tests, yet is still exported from `@mono-agent/memory/search` (a package published to npm, `publishConfig.access: public`) and documented in the package README as current public API with no deprecation notice. That is dead code shipped as a promise to external consumers, which cuts directly against "a lean, understandable core."

## 2 Findings

**F1 — P1 — Schema migration has no column-evolution path; `CREATE TABLE IF NOT EXISTS` is a silent no-op on existing databases.**
`packages/memory/src/store/schema.ts:6` (and every other table in the same function) uses:
```
`CREATE TABLE IF NOT EXISTS memories ( ... )`
```
`packages/memory/src/store/db.ts:355-378` (`persistRecordsUnsafe`) hardcodes the exact column list in its `INSERT`:
```
`INSERT INTO memories (
   id, seq, type, status, text, salience, is_insight, created_at, ...
```
`packages/memory/src/store/db.ts:1006-1016` (`rebuild()`) only issues `DELETE FROM ...` against existing tables — it never re-runs DDL. `git log -- src/store/schema.ts` shows exactly two historical schema changes, both purely additive new tables (`memory_entities`, `content_hashes`, `index_metadata`), so this has never been exercised for a column change and the risk has never manifested — but there is nothing (comment, assertion, or test) stopping the next contributor (human or an AI-agent editing the file) from adding a column the "obvious" way — editing the inline `CREATE TABLE` string — which would then leave every pre-existing on-disk `memory.db` permanently missing that column, breaking every subsequent write with a raw SQLite error. `openMemoryDb()`'s migration loop (`db.ts:120-122`) only runs at all when `readOnly !== true`, so a read-only viewer (e.g. an audit tool, session-web) opening an older DB would never even attempt to catch up. This is precisely the "schema migration safety" risk called out for this territory, and it is unaddressed.

**F2 — P1 — Dead, npm-published "search" API: `VectorMemoryIndex`/`gatherMemoryChunks` have zero consumers and no deprecation notice.**
`packages/memory/src/search/vector-index.ts` (240 LOC, `VectorMemoryIndex`/`createVectorMemoryIndex`) and `packages/memory/src/search/chunks.ts` (91 LOC, `gatherMemoryChunks`/`EntityLike`) implement a full brute-force JSONL embedded vector store keyed on the old v1 `daily/monthly` journal-markdown + entity-graph shape (`MEMORY_SUBDIRS = ["daily", "monthly"]`, `EntityLike { observations, entityType }`). A repo-wide grep for `VectorMemoryIndex|gatherMemoryChunks|MemoryChunk` outside `packages/memory/` (and outside `dist/`) returns **zero** hits — no package (`agent-app`, `session-web`, `memory-supermemory`, etc.) imports any of it. Yet `packages/memory/src/search/index.ts:14` re-exports it, `packages/memory/package.json` sets `"publishConfig": {"access": "public"}`, and `packages/memory/README.md:198` lists `createVectorMemoryIndex`, `gatherMemoryChunks` as current public API with no "legacy"/"deprecated" language. This is real, functioning, tested code that duplicates the now-canonical SQLite+sqlite-vec recall path and ships to npm as if it were live, current API — a contradiction of "a lean, understandable core" and a maintenance/confusion liability for anyone building an external plugin against this package.

**F3 — P2 — `store/db.ts` is a 2,696-line file mixing four unrelated concerns, hurting the "lean, understandable core" premise.**
`packages/memory/src/store/db.ts` combines: (a) the `MemoryDb` SQL persistence class (lines 92-1993), (b) replay-projection CAS validation (`validateReplayProjectionReplacement`, `hasReplaySupersedeCycle`, etc., lines ~1995-2214), (c) canonical-graph replacement CAS validation (lines ~2216-2457), and (d) ~220 lines of bespoke natural-language relation-direction heuristics for the `expandEntityRelations` tool path (`relationDirectionMatches`, `possessiveRoleAfter`, `entityPhraseMatch`, `canonicalWords`, lines 2474-2673 — regex-driven POS-ish parsing of "Morgan's manager" vs "who manages Morgan" style queries). Each concern is well tested in isolation, but a contributor reading "the memory store" has to wade through query-direction linguistics to find the SQL layer and vice versa. This is the single largest legibility risk in scope for the premise's "a lean, understandable core open to external plugins."

**F4 — P2 — Embedding-provider error taxonomy is inconsistent: HTTP failures are typed, network/timeout failures are not.**
`packages/memory/src/search/embeddings.ts:276-284` (`withTimeout`) wraps every provider's `fetch` call in an `AbortController`-based timeout but has no `catch` — a timeout produces a raw `DOMException`/`AbortError`, and a connection failure (Ollama/LM Studio not running — a very common real-world case for these two local-first providers) produces a raw Node `TypeError`/`FetchError`. Meanwhile every *other* failure mode (non-OK HTTP status, malformed response shape, bad constructor options) is wrapped in the package's own typed `MemorySearchError` with a stable `code` (`embedding_request_failed`, `embedding_response_invalid`, etc. — `search/types.ts:1-8`). No code in `search/__tests__/embeddings.test.ts` exercises the timeout or network-failure path. Operators debugging "why did recall/capture fail" get a structured, coded error in most cases and an opaque stack trace in the two most likely local-outage cases — a gap against "honest ops."

**F5 — P3 — Endpoint validation is inconsistent across the three embedding providers.**
`LmStudioEmbeddingProvider` (`embeddings.ts:105`) validates its endpoint through `normalizeServiceRoot` (`embeddings.ts:256-274`), rejecting non-HTTP(S) schemes and endpoints carrying embedded credentials/query/fragment. `OllamaEmbeddingProvider` (`embeddings.ts:42`) and `OpenAIEmbeddingProvider` (`embeddings.ts:156`) only strip a trailing slash — no scheme check, no credential/query rejection. Git blame shows LM Studio support was added later (`0a7c1a1e`, #236) with the stricter helper but the two older providers were never retrofitted. Low exploitability (endpoints are operator-supplied local config, not attacker input) but a real inconsistency a stranger reading the file would not expect.

**F6 — P3 — `MemoryDb`'s constructor performs a filesystem write (`mkdirSync`) even when opened `readOnly: true`.**
`packages/memory/src/store/db.ts:107-108`:
```
if (options.path !== ":memory:") {
  mkdirSync(dirname(options.path), { recursive: true });
}
```
runs unconditionally, before the `readOnly` branch is checked (`db.ts:110-113`). A read-only open against a database whose parent directory does not yet exist will first silently create that (empty) directory tree and then still throw on the subsequent `fileMustExist: true` open. Given this audit's own constraint that live-instance SQLite access must be strictly read-only, a "read-only" option that has a filesystem side effect is a small but real leak in that contract. No test in `open.test.ts` covers `readOnly: true` against a missing parent directory.

## 3 Dead code

- **`packages/memory/src/search/vector-index.ts` (240 LOC) + `packages/memory/src/search/chunks.ts` (91 LOC)** — `VectorMemoryIndex`, `createVectorMemoryIndex`, `gatherMemoryChunks`, `EntityLike` type. Why dead: zero consumers outside their own `__tests__` and the package's own re-exports (`search/index.ts`); superseded entirely by the SQLite+sqlite-vec path in `store/db.ts`. Proposed disposition: delete, or if kept for external plugin authors, mark `@deprecated` in both the source JSDoc and `README.md`'s Public API section and stop describing it as current API. Proof hints: `grep -rln "VectorMemoryIndex\|gatherMemoryChunks\|MemoryChunk\b" packages apps | grep -v packages/memory` → no hits; `packages/memory/README.md:198` still advertises it.
- **`recency` field of `RecallWeights` and `decayGamma`/`DEFAULT_DECAY_GAMMA` of `MemoryDbOptions`** (`store/types.ts:136,203,219,226`; `store/ranking.ts:28` `_decayGamma`/`_now` unused params) — intentionally inert, and honestly commented ("Access time is telemetry, never relevance... do not feed it into the scorer" / "Retained for API compatibility; access-recency scoring is disabled"). Not exposed through any agent-app config surface (verified: no hits outside the memory package), so no user is misled by a config knob that silently does nothing. Disposition: fine to keep through v1 (honest, tested via `decay.test.ts`), candidate for deletion in a later major version since the fields add constructor surface with zero behavior.
- **`"about"` `MemoryEdgeKind`** (`store/types.ts:52`, `schema.ts:33` CHECK constraint, `db.ts:938` `expand()` traversal `kind IN ('thread','about')`, `db.ts:1294/1313` canonical-graph wipe/read sets) — a full edge kind, present in the public `MemoryEdgeKind` type and traversed by `expand()`, that is never inserted anywhere in the codebase (`grep -rn "'about'"` shows only reads/comments, no writer). `db.ts:1277-1278`'s own comment says: "Canonical graph `about` edges are intentionally empty in v1 and are retired together with stale `supports` rows." Disposition: either actually retire the kind from the type/CHECK constraint (breaking-ish, needs a migration itself — see F1) or add one line documenting it as reserved/unused so a stranger doesn't go hunting for its producer.

## 4 Deprecation & legacy

Only one `@deprecated`-tagged item exists in scope:

- **`MemoryDb.applyDecay()`** (`store/db.ts:1979-1988`) — tagged `@deprecated`, documented as a compatibility no-op ("Salience is a static canonical Bullet field in v1... Kept as a compatibility no-op so older integrations can upgrade"). Classification: **removable-now** as far as internal callers go — `bujo/__tests__/reflect.test.ts` and `bujo/__tests__/consolidate.test.ts` `vi.spyOn(db, "applyDecay")` specifically to assert it is *never* called by the current reflect/consolidate pipelines. It is **load-bearing only as external-package API compatibility** (any older direct consumer of `@mono-agent/memory/store` calling `applyDecay` keeps getting `{ decayed: 0 }` instead of a `TypeError: not a function`). Safe to keep through v1; a real removal candidate for a future major bump once external-compat is no longer promised. Well tested (`store/__tests__/decay.test.ts`, `store/__tests__/no-embeddings.test.ts`).

No other `@deprecated`/`@legacy`/`LEGACY` markers exist in `store/**` or `search/**` (verified via grep). The `search/` legacy vector-index surface (F2 / dead code above) is *not* marked deprecated anywhere despite functionally being legacy — that mismatch is itself part of F2's finding.

## 6 Skill-worthy flags

- **`pi-upstream-recon`-adjacent gap, but really a new pattern for `new-package`/`verify-green`: no skill currently checks "does this DDL change need a migration?" before a schema.ts edit lands.** A lightweight addition to `verify-green` (or a standalone check) that diffs `schema.ts` against the previous release tag and fails CI if an existing `CREATE TABLE` statement's column list changed (rather than only new tables/statements being appended) would catch F1 mechanically before it ever ships. Seed command: `git diff <last-release-tag> -- packages/memory/src/store/schema.ts` reviewed for "did an existing CREATE TABLE string change" vs "was a new statement appended."
- **`docs-sync` gap: package README "Public API" sections are not checked against actual internal consumers.** F2 (dead public search API) would have been caught by a periodic "for each exported symbol in a package's Public API README section, is it imported by at least one other workspace package or does it carry an explicit deprecated/experimental label?" pass. Worth folding into `docs-sync`'s per-PR or PR-range audit as an occasional whole-package sweep, not just per-PR deltas.
- **No existing skill covers "error taxonomy completeness" for provider-shaped code** (F4). When wrapping any external network call in a custom typed-error class, a skill/checklist reminder to also cover the timeout/`AbortError`/connection-refused paths (not just non-2xx and malformed-body) would generalize beyond memory embeddings to any future provider adapter (channels, LLM providers, MCP clients).
