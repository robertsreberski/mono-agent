## Freeze-blockers

### Confirmed freeze-blockers
**NONE.**

### Rejected freeze-blockers (downgraded to P1 non-blocking; two-key rule applied)
- **G1-1** (native `notify` missing from composer refs) — REJECTED. Real shipped feature invisible in a
  reference that claims exhaustiveness. The feature *works* and is documented in `feature-registry.md`; the
  composer just can't discover it. Documentation-completeness defect, not a secret/license/correctness
  catastrophe and not runtime-honesty-falsifying.
- **G1-2** (playbook 6 teaches the superseded pattern) — REJECTED. The taught config still functions
  (posts via a valid `SlackSendMessage` tool); it is one feature-generation stale vs the doc it claims to
  mirror. Doc-freshness quality gap, not a hard ship-blocker.
- **G1-3** (per-trigger model/effort undocumented) — REJECTED. Same class as G1-1: a real, validated,
  config-only capability absent from the "exhaustive" table. P1 completeness gap.

Rationale (identical to V6's disposition of the parallel E1-1/2/3): the freeze bar is "blocks a DoD clause /
secret-license-correctness catastrophe / makes honest ops false." All three are **content-accuracy defects in
a bundled skill's reference tables** whose underlying framework *code* is correct and shipping (notify and
per-trigger-model both work — they're in `feature-registry.md` and exercised in `cron-adapter`/`webhook-adapter`).
The worst realistic harm is a composed agent's operator being told a real feature doesn't exist — a genuine
quality regression in the agents this skill produces (strong P1s Robert should clear in the pre-freeze
doc-sweep), but it exposes no secret, corrupts no data, and does not make the running agent misreport what it
did. None halt the freeze. For cross-cluster consistency I hold the same line V6 held.
