# E4-security-deprecation-sweep — security & deprecation cross-cutting sweep

## 1 Verdict & maturity grade

**Grade: B-**

The load-bearing security primitives are genuinely good: a single shared `assertSafeBind`/`isLoopbackHost` module (`packages/agent-contracts/src/host-safety.ts`) is reused by every HTTP-serving adapter (webhook, openai-api, session-web, tui, live) with `allowNonLoopback` defaulting to `false` everywhere, and live-instance configs (personal-agent + all 8 a8c-agents) correctly keep secrets in gitignored `.env` files with a `tokenEnv`-style indirection rather than embedding them in `mono-agent.config.json`. Command execution consistently uses `execFile`/`spawn` (argv arrays, no shell interpolation) rather than shell-string `exec`. The deprecation/legacy surface is unusually well-behaved: none of the 61 files are dead weight and each carries a legible reason to exist (mostly real data-migration compatibility for BuJo memory, continuation-store v1→v2, and the tool-rename alias table).

The grade is held down by a secret-scanning gap this project should care about most: gitleaks — the sole automated secret scanner, run identically in CI and locally — has no rule for Telegram Bot API tokens and its generic-api-key catch-all silently fails on that exact token shape (proven empirically below). Telegram is this framework's flagship channel. There is also no dependency-vulnerability scanning (no `pnpm audit`, no Dependabot) and npm publishing carries no provenance attestation despite running entirely inside public GitHub Actions where enabling it is trivial. None of this is a P0 (nothing has actually leaked; the real bot token sitting in the repo root is correctly gitignored and never committed), but the audit trail below shows the safety net has a hole exactly where this project's threat model needs it most.

## 2 Findings

**F1 (P1) — gitleaks has no rule for Telegram Bot API tokens, and its generic catch-all fails on that exact format.**
`.gitleaks.toml` (repo root) only adds allowlists (`useDefault = true`, plus placeholder-secret exemptions); it defines no custom `[[rules]]`. CI pins `ghcr.io/gitleaks/gitleaks:v8.30.1` (`.github/workflows/ci.yml:48`) and `scripts/check-secrets.mjs:8` runs the identical `gitleaks dir --redact --no-banner --config .gitleaks.toml .` locally via `pnpm run check:secrets`. I reproduced this empirically in an isolated scratch git repo with the same gitleaks binary/version:
- A random 40-char secret under a `token =` key **is** caught by the `generic-api-key` rule (entropy 4.65, `RuleID: generic-api-key`).
- The exact real-world Telegram bot-token shape (`digits:base64-like-35-chars`, e.g. `123456789:<random>`) embedded in JSON as `"telegram":{"botToken":"123456789:<random>"}` is **not** caught — `no leaks found` — even though the un-prefixed random string alone (no leading `digits:`) *is* caught. The embedded colon breaks the generic-api-key regex's capture.
- Running `gitleaks dir` against the actual repo root today also reports `no leaks found`, even though `mono-agent.config.json` (repo root, confirmed below) holds a real 46-character Telegram bot token in exactly this shape.

This means the one secret-scanning gate this repo relies on gives false confidence for the credential type most central to the project's flagship channel (Telegram — see `telegram-interactive-features.md`, `TelegramAskButtons` memory notes). If someone ever `git add -f`'d the root config, or a future contributor lost the `.gitignore` entry, neither CI's `Check secrets` step nor local `pnpm run check:secrets` would catch it.

**F2 (P0-adjacent confirmation, not a live leak) — root `mono-agent.config.json` holds a real Telegram bot token, but was never committed.**
`mono-agent.config.json` (repo root) is **untracked**: `git ls-files -- mono-agent.config.json` returns empty, `git status --porcelain --ignored` shows `!! mono-agent.config.json`, and `git log --all --oneline -- mono-agent.config.json` returns **zero** commits — confirmed never committed in this repo's history. It is listed in `.gitignore:17` (`mono-agent.config.json`). Its `telegram.botToken` field is a 46-character string (shape-consistent with a real bot token), while every other config field is small/structural. This file is the developer's own scratch/dev config; it is not shipped, not published, and not a repo secret leak — but see F1: it demonstrates the exact scenario the scanning gate cannot actually catch, and it's inconsistent with the project's own best practice observed in every live instance (F-below), where secrets live only in `.env` + a `tokenEnv`-name indirection in the JSON config, never inline.

**F3 (P2) — no dependency-vulnerability scanning anywhere in CI.**
`.github/workflows/ci.yml` has no `pnpm audit` step, no `.github/dependabot.yml` exists, and no `dependency-review-action`. The only OSS-hygiene gate, `scripts/check-oss-hygiene.mjs`, is a **privacy/PII leak scanner** (checks tracked files for non-synthetic consumer-fixture names and real home-directory paths like `/Users/<realname>`) — it does not check package vulnerabilities at all, despite the name inviting that assumption. For a framework meant to be "brought" into other people's agent instances (recipes, plugins, 21+ published packages), there is currently no automated signal if a transitive dependency ships a known CVE.

**F4 (P2) — npm publish carries no provenance attestation; uses a classic token, not OIDC trusted publishing.**
`scripts/release/publish-release.mjs:303-313` builds the publish invocation with `npm publish <tarball> --access <access> --tag <distTag>` and never adds `--provenance`. `.github/workflows/npm-release.yml:73-76` authenticates via `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}` (a classic long-lived npm automation token), not npm's OIDC-based trusted publisher flow. The release runs entirely inside public GitHub Actions (`ubuntu-latest`, no self-hosted runner), which is exactly the environment where `--provenance` (or trusted publishing) is a low-effort, high-value hardening step — every one of the ~21 `@mono-agent/*` packages a user installs today carries no cryptographic build attestation.

**F5 (P3) — `minimumReleaseAgeExclude` is configured but the policy it exempts from is never turned on.**
`pnpm-workspace.yaml:13-24` lists 11 exact pinned packages (`@earendil-works/pi-agent-core@0.80.5`, `@anthropic-ai/claude-agent-sdk-*@0.3.206`, etc.) under `minimumReleaseAgeExclude`. No `.npmrc` exists anywhere in the repo (`find . -iname .npmrc -not -path "*/node_modules/*"` → empty), no CI step sets `minimumReleaseAge`, and `pnpm config get minimumReleaseAge` returns `undefined`. pnpm's minimum-release-age guard (a real supply-chain control against just-published/compromised-account npm releases) is therefore never actually enabled — the exclude list looks like an active security control but currently exempts packages from nothing.

**F6 (P3) — inconsistent file permissions across live-instance `.env` secrets.**
Of the 8 `~/a8c-agents/*/` instances, 3 (`activity-digest/.env`, `p2-watcher/.env`, `slack-sweep/.env`) are mode `644` (world/group-readable) while the other 5 plus `~/personal-agent/.env` are mode `600`. Same split on the paired `mono-agent.config.json` files (3 at `644`, 5 at `600` — though the `644` config.json files themselves hold no inline secrets, only `tokenEnv` name references, so the immediate risk is limited to the `.env` files). Paths only; no values read or reproduced.

**F7 (P3, recon-hint correction) — the "2 `as any` in src" lead does not reproduce at HEAD.**
`grep -rnE '\bas any\b' packages/*/src --include="*.ts"` (excluding tests/dist) and a whole-repo variant both return **zero** matches at commit `5f27a0ec`. Either the casts were already removed before this audit or the recon hint was inaccurate; flagging per the audit's "verify recon hints" instruction rather than asserting a finding that doesn't exist.

## 3 Dead code

None found in this sweep's scope. Every file matched by the `legacy|back-compat|backward` grep (see §4) is either reachable/exercised production compatibility code, or a naming-only false positive (nothing to delete because there was never a compat surface there). The 3 canonical `@deprecated` functions (`reflect()`, `decay()`, `applyDecay()` in the memory package) are intentional permanent no-ops, not dead code — they are still invoked via the shipped `memory-bujo reflect` CLI subcommand (`packages/memory/src/bujo/cli.ts:99`) and are honestly documented as read-only compatibility probes in both the code comments and `docs/memory/*.md` (see §4).
