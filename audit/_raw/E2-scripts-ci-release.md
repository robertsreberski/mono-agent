# E2-scripts-ci-release — scripts, CI & release lane

## 1 Verdict & maturity grade

**Grade: C+.** The engineering craftsmanship in this territory is genuinely excellent and unusually honest: `build-with-provenance.mjs`, `scripts/release/*`, and `fleet-green-check.mjs` are fail-closed almost everywhere I looked — TOCTOU-closing double-reads, owner-only markers, frozen tarball integrity, npm-credential scrubbing, staged-then-promoted dist-tags. I found zero fake-success paths and zero shortcuts that quietly turn a failure into a pass. The actual npm release history (verified live against the public registry: `0.1.0` → `0.11.2`, `0.7.0` correctly absent as CHANGELOG.md claims) matches every claim in CHANGELOG.md exactly.

The grade is C+, not A/B, because the **one artifact this territory exists to produce — a trustworthy "is v1 ready to freeze" signal — has a real, evidenced gap**: `fleet-green-check.mjs`'s own rule is "no comment on a given day = not a green day, the counter resets" (`scripts/fleet-green-check.mjs:39-40`), yet nothing on the live fleet host actually runs it daily (verified: no launchd job, no crontab entry — see F1), and the actual GitHub issue #119 comment history already has a 2-day silent gap (2026-07-13 and 2026-07-14) that, by the tool's own rule, has already reset the 7-day counter. Separately, `pnpm run verify:all` (the documented "one-shot CI equivalent") and `.github/workflows/ci.yml` are each missing checks the other runs, in both directions (F2) — most importantly, the consumer-contract fixtures that most directly validate the "config-first, agent-in-seconds" premise are **never gated by CI**, only by a developer choosing to run `verify:all` locally.

## 2 Findings

**F1 (P0) — The v1 freeze DoD's sole mechanism has no actual daily automation, and its own counter has already reset.**
`scripts/fleet-green-check.mjs:39-40`:
> "No comment on a given day = not a green day; the 7-consecutive-day counter is human-audited from the dated comments."

`skills/fleet-deploy/SKILL.md:153-155`:
> "Generic auto-discovery checks every matching plist it finds; it cannot prove that a removed plist still belongs to the fleet. The installed nightly job and all deployment evidence therefore use `--expect-labels`..."

This documents an *"installed nightly job"* as fact. I verified, read-only, against the live fleet host (the same Mac whose `~/Library/LaunchAgents` plists — `com.mono-agent.finances-e9c073d7`, `-inner-child-fdfc3392`, `-personal-agent-059657c8`, `-transcription-f4a742c8` — exactly match the `FLEET_LABELS` four-label set the same SKILL.md hardcodes at line 129):
- `launchctl list 2>/dev/null | grep -i "green\|fleet"` → no output.
- `crontab -l` → "no crontab for robertsreberski".
- `grep -l "fleet-green-check" ~/Library/LaunchAgents/*.plist*` → no matches, across all 40+ installed plists.

There is no installed nightly job anywhere on the one host this matters for. I then read the actual issue history (`gh issue view 119 --json comments`, read-only): 22 comments exist, with `VERDICT:` lines dated 2026-07-07 (5x, including a deliberate RED simulation and 2 real RED runs), 07-08 (RED), 07-09 (RED), 07-10 (RED, sha mismatch), 07-11 (3x GREEN, different shas each time as deploys landed same-day), 07-12 (4x GREEN, four different shas same day) — **then a hole: zero comments for 2026-07-13 and 2026-07-14** — then one comment 2026-07-15T06:02:53Z (GREEN, sha `4ebd8e0`, which is the `4ebd8e02` merge commit two commits *behind* current HEAD `5f27a0ec`). By the script's own rule, this gap already reset the counter, and the mechanism has never yet produced a documented unbroken 7-day run — because nothing forces it to be run daily. This is squarely a "v1 freeze DoD" premise violation: the epic's stated closing condition depends on a process that is manual-invocation-only despite being documented as installed automation.

**F2 (P1) — `pnpm run verify:all` and `.github/workflows/ci.yml` are each missing checks the other enforces, in both directions; the gap that matters most is untested in CI at all.**
`scripts/verify-all.mjs:8-19` (`repoGate`) runs: check:node, check:secrets, check:oss-hygiene, check:codex-discoverability, check:architecture, build, typecheck, test, test:demo, `git diff --check`, then (`verify-all.mjs:63-78`) `verifyConsumers` (the `local-agent-alpha`/`local-agent-beta` consumer-contract fixtures under `packages/agent-app/src/__tests__/fixtures/consumers/`).
`.github/workflows/ci.yml:44-93` runs the same repo-gate steps (via a dockerized `gitleaks` invocation rather than the `check:secrets` script — functionally equivalent, verified `check-secrets.mjs:8` uses an identical `gitleaks dir --redact --no-banner --config .gitleaks.toml` invocation, but against whatever `gitleaks` is on the local `PATH`, not the pinned `v8.30.1` image), **plus** `release:validate` (line 65) and `release:pack` (line 74) and, on the Node 22.19.0 leg only, `release:consumer` (line 78) — none of which `verify-all.mjs` ever calls.
Net result: `verify-all.mjs` never runs `release:validate`/`release:pack`/`release:consumer`, and **CI never runs `verify:consumers` at all** — grep confirms zero references to `verify:consumers` or `verify-consumers.mjs` anywhere in `.github/workflows/*.yml`. The consumer-contract fixtures are precisely the check that validates "simple, quick agent instances from one config in a folder" end-to-end; a change that breaks them can merge on green CI, and will only be caught if a human separately runs `pnpm run verify:all` before or after merging. `skills/verify-green/SKILL.md:15-17` calls `pnpm run verify:all` a "one-shot equivalent" of the "Full gate (CI order)" it lists just above (which also omits `release:validate`/`release:pack`, presented instead as a third, easy-to-skip block at lines 30-34) — the word "equivalent" overstates what either gate actually covers.

**F3 (P2) — CI silently re-runs the demo build/typecheck/test three separate times for no additional coverage.**
`package.json:13` (`"build": "node scripts/build-with-provenance.mjs"`) already chains `build:demo` — confirmed in `scripts/build-with-provenance.mjs:31-34`: `BUILD_COMMANDS = [["pnpm", ["-r", "--sort", "run", "build"]], ["pnpm", ["run", "build:demo"]]]`. `package.json:23-24` (`"typecheck": "pnpm -r --sort run typecheck && pnpm run typecheck:demo"`) already chains `typecheck:demo`. `package.json:25` (`"test": "pnpm run release:test && pnpm run scripts:test && pnpm -r --sort run test && pnpm run test:demo"`) already chains `test:demo`. Yet `.github/workflows/ci.yml:86-93` runs "Build demos" (`pnpm run build:demo`), "Typecheck demos" (`pnpm run typecheck:demo`), and "Test demos" (`pnpm run test:demo`) again, immediately after the steps that already ran them. `scripts/verify-all.mjs:8-19`'s `repoGate` mirrors one of these three (an explicit `test:demo` entry after `test`, which already ran it). This burns real CI minutes for identical re-execution of already-passed commands and is easy to miss because the redundancy is hidden inside `package.json`'s script chaining rather than visible in `ci.yml` itself.

**F4 (P2) — Two real checks are "phantom gates": exercised only because a test happens to call the real function with no mocks, not because any named script/CI step runs them.**
`scripts/check-getting-started-version-pins.mjs` has a full `main()`/CLI entry point (lines 90-108) and a documented purpose (a getting-started doc pin drifting one release behind, per its own top comment citing "goal #164"), but there is no `check:getting-started-version-pins` entry anywhere in `package.json`, `verify-all.mjs`, or either workflow file (confirmed by grep). It is exercised only because `scripts/__tests__/getting-started-version-pins.test.mjs:6-9` happens to call `checkGettingStartedVersionPins()` with **no overrides**, so it does perform a real check against the live `docs/getting-started/*.md` files and the live `packages/agent-app/package.json` version — but this only works today because that one test case's mocking discipline hasn't drifted, and it runs by the accident of matching `scripts/__tests__/*.test.mjs` inside `scripts:test`, not by any named, documented gate.
`scripts/verify-deep-imports.mjs` is the same pattern, independently confirmed by the C2 auditor's report (`audit/_raw/C2-runtime-adapter-vendored.md`, §6): its own file comment (`verify-deep-imports.mjs:12-14`) says it "Runs standalone... part of the phase gate," but it is not a named step in `verify-all.mjs`'s `repoGate`, `package.json`, or either workflow. It is exercised only via `scripts/__tests__/verify-deep-imports.test.mjs:41-56`'s no-mock, real-resolution test case. A future edit to the `scripts:test` glob, or to either test file dropping its no-args case, would silently remove real protection with no named CI step to point at as broken.

**F5 (P2) — `scripts/release/validate-release.mjs` never checks the root `package.json`'s own `@mono-agent/*` devDependency pins — already tracked (issue #228, open), confirmed still present in current code.**
`scripts/release/validate-release.mjs:36-100` (`validateRelease`) reads `rootPackageJson` (line 39) but uses it **only** for the `engines.node` check (line 52-54); the internal-dependency-pin loop (lines 82-94) iterates `publishable` — the catalog packages discovered via `discoverPackages()` — never the root manifest's own `devDependencies` (which pin every `@mono-agent/*` package to `workspace:0.11.2` for local dev/typecheck convenience, per `package.json:42-59`). Today these 18 root pins happen to all be correct, but nothing enforces that on the next release; a stale root pin would pass `validateRelease`/CI/`verify:all` silently. GitHub issue #228 ("Harden release validation for root workspace references") tracks exactly this, opened from the v0.8.0 release review, still open — no new instance found beyond what the issue already describes; disposition confirmed accurate as of HEAD `5f27a0ec`.

**F6 (P2) — `scripts/fleet-green-check.mjs` is a single 2,380-line, ~90-function file — a legibility outlier even for an ops/audit tool.**
No other script in this territory exceeds 900 lines (`scripts/lib/build-provenance.mjs` at 965 is the runner-up, out of this territory's declared scope). The file is dense with near-duplicate guard clauses (e.g. the same five-line "if `X.timedOut === true` return fail" shape repeats roughly a dozen times across `evaluateLoaded`, lines 554-774) and a great deal of TOCTOU-closing double/triple-read logic that is correct but hard to hold in one's head. It is, to its credit, heavily unit-tested — `scripts/__tests__/fleet-green-check.test.mjs` has 17 top-level `describe` blocks and 123 test-level assertions covering nearly every exported pure helper (confirmed by grep, not deep-read line-by-line per the test-skim instruction) — so correctness risk is mitigated, but the "a competent stranger must be able to understand the core" premise clause applies to ops tooling too when that tooling is the literal gate for shipping a version. No single function-level docstring or README maps the ~90 functions to the six checked dimensions the file's own header comment (lines 8-27) describes well in prose.

**F7 (P3, confirmed-accurate, no action needed) — Two already-tracked, honestly-disclosed release/provenance limitations, re-verified against current code.**
- Issue #226 ("Build provenance: support trusted pnpm/git paths on Windows and non-FHS Linux") describes `scripts/build-with-provenance.mjs`'s hardcoded `TRUSTED_GIT = "/usr/bin/git"` (line 29) and `selectBuildInvocation`'s Windows-descendant-of-Node constraint (lines 119-139) as known gaps, explicitly scoped as "does not affect the current macOS Node-24 fleet." Re-verified: both constraints are still present exactly as described; the issue's disposition is accurate and appropriately non-blocking.
- Issue #230 ("Release assurance: trusted npm publishing and isolated packed consumers") tracks the absence of OIDC/trusted-publishing provenance and the single combined packed-consumer fixture (`scripts/release/fixtures/packed-consumer/`, one `npm install` of all 19 tarballs together, which could theoretically mask an undeclared internal dependency). Re-verified live: `npm view @mono-agent/agent-app@0.11.2 --json` has no `provenance`/`attestation` field, and no doc in `docs/`, `README.md`, or `.github/` falsely claims npm provenance — the gap is real but honestly undisclosed-as-a-limitation nowhere claimed otherwise. Minor additional observation not in the issue: each release leaves a permanent `mono-agent-stage-<version>` npm dist-tag behind (confirmed via `npm view @mono-agent/agent-app dist-tags --json`: 7 stage tags accumulated across the 7 releases since 0.8.0) that is never cleaned up — cosmetic registry hygiene debt, P3.

## 4 Deprecation & legacy

No `@deprecated`-tagged symbols exist anywhere in this territory's file scope (`grep -rn "@deprecated"` over `scripts/**`, `.github/workflows/**` returns nothing). The closest legacy-shaped items are:
- **`scripts/lib/build-provenance.mjs` / `scripts/lib/memory-cleanup-calibration.mjs`** — imported by in-scope scripts (`fleet-green-check.mjs`, `build-with-provenance.mjs`, `build-provenance-probe.mjs`, `memory-benchmark.mjs`) but living under `scripts/lib/**`, which is **not** covered by this territory's exact declared scope (`scripts/*.mjs` is non-recursive). Flagging as a **coverage gap**, not a finding: these two files (965 + 916 lines) implement load-bearing marker/digest/lock logic for the build-provenance system and do not appear to be any other territory's named scope either (they are not release/, not `__tests__/`, not workflows). Recommend the synthesis pass confirm someone actually read them.
- **The npm `mono-agent-stage-*` dist-tags** (F7) are not "deprecated" in the code sense but are permanent artifacts of every release that nothing ever prunes — load-bearing for `executeFrozenPublish`'s verify-then-promote flow (removing them mid-flow would be actively harmful), so they should stay, but a periodic prune of *old, already-promoted* stage tags would be reasonable hygiene.
- `.gitleaks.toml`'s allowlist regexes (lines 15-19) exist specifically to keep fixture/test placeholder strings (`dummy-api-key`, `sk-test-secret`, etc.) out of the gate — verified these are allowlist patterns for known-fake values, not exemptions for anything live; no legacy risk found.

## 6 Skill-worthy flags

- **verify-green**: Add an explicit rule that any check with real, non-trivial logic and a `main()`/CLI entry point must have a **named** `pnpm run check:<name>` (or `verify:<name>`) script wired into `repoGate` in `verify-all.mjs` — a check that only "works" because a test happens to call the real function with no mocks (F4: `check-getting-started-version-pins.mjs`, `verify-deep-imports.mjs`, both independently found — the latter by the C2 auditor too) is invisible to anyone reading `package.json`'s script list and fragile to test-file refactors. Concrete check to add to the skill: `grep -L` every `scripts/*.mjs` file that defines an `isCli` block against `package.json` + `verify-all.mjs`'s `repoGate` array; anything missing from both is a phantom gate.
- **verify-green**: Note explicitly in the skill that `pnpm run verify:all` is **not** a strict superset of `.github/workflows/ci.yml` (missing `release:validate`/`release:pack`/`release:consumer`) and CI is **not** a strict superset of `verify:all` (missing `verify:consumers`) — today's "one-shot equivalent" phrasing (`skills/verify-green/SKILL.md:15-17`) overstates the overlap in both directions (F2).
- **fleet-deploy**: The skill documents "the installed nightly job" (`skills/fleet-deploy/SKILL.md:153-155`) as an existing fact; before any future audit or handoff trusts that sentence, it should be re-verified against `launchctl list` on the actual fleet host, not assumed from the doc — this exact gap (documented-but-not-installed automation) is precisely the kind of drift a fleet-deploy skill amendment should force a check for whenever the skill is invoked ("does the daily green-check job actually exist right now, per `launchctl list`?").
- **release-lockstep**: When cutting a release, also spot-check the root `package.json`'s own `@mono-agent/*` devDependency pins against the target version (F5/issue #228) — `validateRelease` does not currently check this, so the skill's own manual verification step is the only guard until E2-7 lands.
